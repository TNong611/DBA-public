# DBA — 双脑架构（Dual-Brain Architecture）

> **DBA** = **D**ual-**B**rain **A**rchitecture，**双脑架构**：一个本地小模型常驻、
> 一个云端大模型按需调用，两者共用同一份可移植记忆。
>
> 本仓库是双脑架构的**记忆层与 Agent 接入层**实现。它不绑定任何客户端 ——
> 换一个 Agent 框架、换一台机器、换一个云端模型，记忆都跟着代码走。

```
D:\AI\DBA\
├── memory/            记忆数据（三层 + 向量层）
│   ├── core.md           核心记忆   云端写  ≤15KB  每轮全量注入
│   ├── stream.md         记忆流     本地写  不限    仅检索（一行一条）
│   ├── ws/<区>.md        工作区册   云端写  不限    仅检索（存细节）
│   ├── .index/           关键词倒排索引（CJK 二元组 + BM25）
│   └── .vec/             向量索引（bge-m3，Ollama GPU）
├── scripts/           实现（nb_*：索引/检索/组装/写入/迁移）
├── port/              Agent 快速移植接口 ← 接入只需这一个文件
├── integrations/      各客户端的适配器（DSH / Hermes）
├── docs/              架构与接入文档
└── backups/           迁移前备份
```

---

## 一、为什么是「双脑」

单靠云端大模型，问题是**记忆不在你手里**：上下文一过期就断片，且每轮都要把
全部记忆重新塞进 prompt 付钱。单靠本地小模型，问题是**推理不够**。

双脑架构把两者拆开：

| | 本地脑 | 云端脑 |
|---|---|---|
| 硬件 | 本机 GPU（Ollama） | 远端 API |
| 职责 | 保持**状态连续性**、嵌入、记忆流写入 | 推理、决策、核心与细节记忆写入 |
| 时标 | 常驻、连续（主时标） | 按需唤醒（顾问） |
| 典型模型 | bge-m3（嵌入）/ 本地生成模型 | DeepSeek / GPT / Claude 等 |

关键设计：**记忆不属于任何一脑**。它是磁盘上的一组文件，两脑都读写它。
本地脑负责「不间断地记流水」，云端脑负责「把流水提炼成事实和细节」。

## 二、记忆的三层 + 一层向量

### 三层（记事本架构）

| 层 | 文件 | 写者 | 容量 | 怎么用 |
|---|---|---|---|---|
| **核心记忆** | `core.md` | **云端模型** | **≤15KB 硬限** | **每轮全量注入**，不检索 |
| **记忆流** | `stream.md` | **本地模型** | 不限 | 仅检索，**一行一条「何时干过什么」** |
| **工作区册** | `ws/<区>.md` | **云端模型** | 不限 | 仅检索，存细节/结论/报错与修法 |

写入者分离不是分工洁癖，是**信息可得性**决定的：

- 核心记忆和工作区册要的是**提炼**（把一轮对话压成一条硬事实），
  只有看得见完整上下文的云端模型做得到。
- 记忆流要的是**不间断的流水**，且必须极便宜（每轮都写），所以归本地模型。

容量策略也不同：核心记忆**全量注入**，所以必须硬限 15KB；另外两层**只被检索**，
所以不限长度 —— 它们的增长不推高每轮 token 成本。这是与旧「五级记忆」
（层层压缩、层层有配额）最根本的区别：**注入量随话题浮动，不随记忆总量增长**。

### 一层向量（语义通道）

关键词索引是**精确 token 匹配**，查「记忆架构」只命中含这些字的段落。
它的弱项是**同义改写**：

```
查「怎么让模型记住我」  →  关键词查不到（没这几个字）
                        →  向量查得到（语义上就是「记忆连续性」）
```

所以另建一层向量索引，与关键词索引**零耦合**：

- **零耦合是可靠性要求，不是洁癖。** 向量层依赖 Ollama 进程 + GPU；关键词层
  是纯 Python 零依赖。若把两者串在一个入口里，Ollama 一挂就**整个检索全哑**，
  连本来能用的精确检索也没了。现在任一方挂掉，另一方照常返回，
  并且结果里会**明确标出哪条通道降级了**（静默降级在本项目里已造成过实际损失）。
- 两个索引**切分单元一致**（都走 `nb_index.collect_docs()`），否则同一个问题
  在两边命中不同粒度的段落，合并时会重复或缺漏。

## 三、每轮的数据流

```
用户输入
   │
   ├─→ 本地脑：以输入为 query 检索记忆（关键词 + 向量）
   │            ↓ 产出 _core_context.md（稳定）+ _hits_context.md（每轮变）
   │
   └─→ 云端脑：收到 [核心记忆全量] + [本轮检索命中] + 用户输入
                ↓ 推理
                ↓ 需要更多记忆时，可**主动再次检索**（这是设计内的）
                ↓ 需要记东西时，写 core.md / ws/*.md
```

注入分两段是**前缀缓存**的要求：

- `_core_context.md` 几天才变一次 → 排在 prompt **前部**，稳定内容在前，
  前缀缓存才能命中。
- `_hits_context.md` 每轮都变 → 排在 prompt **最末尾**。

两者若合成一段，检索一命中就会让 system prompt 从该段起整段变化，
其后所有段落（工具定义、人格段）的缓存全部失效。实测差距：**92.7% → 0%**。

## 四、快速接入（三步）

```python
import sys; sys.path.insert(0, r"D:\AI\DBA\port")
import dba

# 读
r = dba.recall("用户之前提过的代理地址")      # 自动选通道，返回 {hits, text, degraded...}
print(r["text"])                              # 直接可塞进 prompt 的文本

# 读（三级阶梯：内容太多则二次检索 + 时间权重；不清晰则主动再检索）
r = dba.recall("用户之前提过的代理地址", mode="ladder")
print(r["relaxed"])       # 放宽过哪些条件（空 = 一次就查到）
print(r["weak"])          # 放宽后仍不清晰？→ 该换个说法自己再查
print(r.get("time"))      # 时间权重是否真生效（含「等于没生效」的情形）

# 每轮双方信息进入本地模型；先持久化，再异步处理
result = dba.ingest_turn({
    "session_id": "会话ID", "event_id": "轮次唯一ID",
    "user": "用户输入", "assistant": "云端输出",
    "at": "2026-10-06T12:00:00+08:00",
})
# 云端读取完整脱敏事件，必须检查 degraded/errors
turns = dba.recall_turns("双方之前讨论过什么", top_k=5)

# 写（按写入者分工）
dba.remember_core("新硬事实", title="标题")    # 云端模型用
dba.remember_stream("干过什么", tag="标签")     # 本地模型用
dba.remember_ws("工作区名", "细节", title="标题")  # 云端模型用
```

接入方**不需要**知道仓库在哪、索引叫什么、Ollama 跑没跑 —— `port/dba.py`
自己定位仓库根（`DBA_HOME` 环境变量可覆盖），并在某一通道不可用时
**明确报告降级**而不是静默少给结果。

### 双方信息持续写入

DSH 钩子在一轮结束后把用户输入和助手文本交给 `nb_turn.py`。脱敏事件先保存在 `memory/.turns/events/`，本地 `RWKV-7 1.5B`（CUDA BF16）联合提炼成一条不超过 90 字的记忆流，并按会话保存可恢复递归状态；`bge-m3` 对完整事件分块编码，保存在 `.turns/vectors/`。关键词、记事本向量和事件向量分别记录成功或失败，失败事件保留并可重试。Windows 用户级任务 `DSH_DBATurnRetry` 每 5 分钟调用 `scripts/dba-turn-retry.ps1`，不依赖下一轮用户消息触发重试。核心记忆和工作区仍由云端写入。

RWKV-7 运行于独立 `.venv-rwkv` 的 CUDA BF16 环境，强制拒绝 CPU；`bge-m3` 继续通过 Ollama GPU 编码。RWKV 状态文件带模型 SHA-256 指纹、会话 revision 和事件收据，原子保存并支持崩溃恢复、重复事件幂等。

```powershell
py -3.14 scripts/nb_turn.py status
py -3.14 scripts/nb_turn.py retry
py -3.14 scripts/nb_turn.py recall "之前讨论的记忆方案"
py -3.14 scripts/nb_turn.py live-test  # 临时目录中的真实 GPU 全链路测试
```

每轮组装会自动召回事件文本片段，完整事件可通过 `dba.recall_turns()` 读取。RWKV 负责连续状态与本地整理，`bge-m3` 负责独立向量编码。钩子源码更新需宿主重新加载后才生效。用户消息与每条助手消息会原子保存脱敏草稿到 `.turns/drafts/`；重启恢复时，中断轮次附明确标记后入队。没有助手文本的中断轮次保留草稿，不伪造回复。持久化粒度是消息事件，尚不包含未形成消息的流式 token。加载版本可读取 `.turns/hook-runtime.json`（当前 `joint-turn-draft-v3`）。

### 检索规则（三级阶梯）

| 级 | 触发 | 做什么 |
|---|---|---|
| ① 一次检索 | 总是 | BM25 `top_k`，**纯相关度，不掺时间** |
| ② 二次检索 | 命中总量 > 6KB（「内容太多」） | 收窄到行窗口 **+ 时间权重重排**（越近权重越大） |
| ③ 主动再检索 | 结果不清晰（0 命中／最高分 <6／无共享词） | 逐级放宽，最多 2 次，每次记进 `relaxed` |

时间权重 = `0.5 ** (距最新天数 / 30)`，**下限 0.5**，按
`相关度 × 权重` 相乘排序；**无日期的段取中性权重**（有日期段的中位数 0.724）
—— 「不知道」不奖不罚（既不说它最新，也不说它最旧）。

> ⚠️ `time` 字段存在**不等于**时间权重起了作用：语料无日期或只跨 0 天时
> 权重全是 1.0，排序与不加时间完全一致。所以结果里带 `span_days`，
> `note` 也会如实写「未生效」—— 不说明就等于把「没发生」说成「发生了」。

详见 [`docs/接入指南.md`](docs/接入指南.md)。

## 五、可移植性

整个 `DBA\` 目录是自包含的：

- **数据跟着代码走**：默认 `memory/` 就在仓库内，不再依赖 hermes 之类的客户端目录。
  （2026-10-06 从 `%LOCALAPPDATA%\hermes\memories\` 迁出，理由见 `docs/迁移记录.md`。）
- **路径可覆盖**：设 `DBA_HOME` 即指向另一份仓库，插件与门面都会跟随。
- **git 可托管**：`.gitignore` 已排除大体积索引与运行态产物，只提交记忆正文与代码。
  同步到 GitHub 或域名自建服务时，记忆正文随仓库走。
  ⚠️ **索引不进版本库**（`memory/.index/`、`memory/.vec/`）：它们整体重写、无法增量
  diff，进 git 会把历史撑爆。克隆后跑一次 `py nb_rebuild.py` 即得（约 16 秒）。
- **换 Agent 不用改记忆**：接入层只有一个 `port/dba.py`，别人家的 Agent
  也可以照同一个接口接。

## 六、依赖

| 组件 | 必需 | 说明 |
|---|---|---|
| Python 3.14 | 是 | 脚本用 `py -3.14` |
| numpy | 向量层 | `py -3.14 -m pip install numpy` |
| Ollama + `bge-m3` | 向量层 | `ollama pull bge-m3`；**必须走 GPU** |
| 无 | 关键词层 | 纯标准库，零依赖 |

**GPU 是硬要求。** 向量层不做「GPU 不可用就退回 CPU」的兜底 —— 那只会让慢到
不可用的路径悄悄生效，人还以为在用 GPU。拿不到 GPU 就直接报错。

## 八、自检

```powershell
py -3.14 D:\AI\DBA\scripts\nb_doctor.py            # 全部检查
py -3.14 D:\AI\DBA\scripts\nb_doctor.py --quiet    # 只报失败（给计划任务/CI）
```

查 7 项：路径（含「旧位置有没有复活」）、编码（含中文的 `.ps1` 有没有 BOM）、
关键词索引、向量层（**含 GPU 是否真的在用**）、集成副本是否与生效位置一致、
计划任务上次是否成功、写入闸门是否还在拦垃圾。

存在的理由：本项目的故障几乎都是**静默**的 —— 脚本 exit 0、日志有输出、
看起来一切正常，只是记忆写去了错的地方、或检索永远返回 0 命中。
人工逐项检查不可靠，所以固化成命令。**修完东西跑一次，别靠感觉。**
