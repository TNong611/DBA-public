> **DBA** = **D**ual-**B**rain **A**rchitecture，双脑架构：一个本地小模型常驻、

## §1 双脑架构总述

### 1.1 为什么必须是两个脑

单靠云端大模型，问题不是能力，是**归属**：记忆不在你手里。上下文一过期就断片，
而且每一轮都要把全部记忆重新塞进 prompt 付一次钱 —— 记忆越攒越多，每轮越贵。

单靠本地小模型，问题是**推理不够**：它能记住、能嵌入、能跑流水，但做不了复杂决策。

把两者拆开，各自承担它便宜的那部分：

| 维度 | 本地脑 | 云端脑 |
|---|---|---|
| 运行位置 | 本机（Ollama `http://127.0.0.1:11434`） | 远端 API（DeepSeek / GPT / Claude 等，可替换） |
| 时标 | **常驻、连续**（主时标） | **按需唤醒**（顾问） |
| 每轮职责 | 拿用户输入当 query 检索记忆 → 产出两段注入文本；写记忆流 | 收到「核心记忆全量 + 本轮命中 + 用户输入」→ 推理、决策 |
| 写入产出 | `memory/stream.md`（一行一条「何时干过什么」） | `memory/core.md`（硬事实）、`memory/ws/<区>.md`（细节/结论/报错修法） |
| 算力角色 | 嵌入模型的宿主（bge-m3 走 GPU，向量层的算力来源） | 提炼与判断 |
| 成本特征 | 便宜，可以**每轮都跑、不间断** | 贵，必须按需 |
| 挂掉的后果 | 检索哑 → 想不起细节（但记忆还在盘上） | 没得推理（但记忆还在盘上） |

### 1.2 「记忆不属于任何一脑」是这份架构的地基

这是比「用哪两个模型」重要得多的设计决定：

> **记忆是磁盘上的一组文件，两脑都只是它的读写方。**

具体落法是：

- 记忆正文（`core.md` / `stream.md` / `ws/*.md`）与索引（`memory/.index/`、`memory/.vec/`）
  **全部在仓库内**，不放在任何客户端的安装目录里（2026-10-06 从 `%LOCALAPPDATA%\hermes\memories\`
  迁出，理由：hermes 只是某台机器上某款客户端的目录，记忆是可移植资产，
  埋进去等于要求所有接入方都装同一款客户端并遵守它的目录习惯）。
- 路径可覆盖：`DBA_HOME`（兼容旧名 `FOXNOTE_HOME`）一设，插件、门面、脚本全部跟随。
  整目录 `git clone` / 拷走即用。
- 换云端模型、换 Agent 框架，**记忆正文一个字都不用改**；接入层只有
  `port/dba.py` 一个文件。

### 1.3 连续状态与云端关系推理：当前方向及验收边界

> 本节记录本次 RWKV 状态接口讨论与实测结果。它是设计方向与实现边界，不是全部完成声明。

**连续状态负责“还在场”，Transformer 负责“这次对齐哪些关系”。** 两者是能力侧重，不是互斥分工。不能把本地模型降格为摘要器，也不能把关键词检索当成连续状态的替代品。

| 信息通道 | 职责 | 保存与消费 |
|---|---|---|
| RWKV 连续状态 | 在线累积跨轮上下文、慢变量与约束 | 完整状态留本地，按会话恢复；状态输出接口尚待训练 |
| 记事本与原始事件 | 保留可核对、可逐字召回的事实证据 | 关键词与 bge-m3 语义检索返回原文；不靠状态重建原文 |
| 云端 Transformer | 当前窗口的实体绑定、否定、多跳关系与复杂决策 | 消费当前输入、核心记忆、检索原文及未来状态接口输出 |

目标闭环：

```text
用户输入 + 云端输出
    ├─ 脱敏事件日志 → 关键词/语义索引 → 按需召回原文
    └─ RWKV 更新连续状态 S → 本地原子快照
                                 └─ 状态输出接口（待完成）
                                      ├─ 可读固定槽位（近期实验）
                                      └─ 专用记忆码/连续前缀（后续研究）
下一次云端调用：
核心记忆 + 当前输入 + 检索原文 + 状态接口输出
    → Transformer 推理 → 输出作为下一轮 RWKV 观测
```

#### 已实现不等于最终方案已完成

- RWKV-7 World 1.5B v3 权重已在 RTX 5060 Laptop 上运行 CUDA BF16；用户与助手联合事件可进入递归状态。
- 完整状态按会话保存，包含模型指纹、revision 和事件收据；已有原子快照、恢复、重复事件幂等与摘要分支隔离测试。
- bge-m3 独立编码完整事件，持久化事件向量；已有隔离钩子到 GPU 整理、召回与云端文本注入的端到端测试。
- 云端目前收到文本摘要和检索原文，**不收到 RWKV 状态张量或专用状态记忆码**。
- 当前实现是事件 worker 调用独立 RWKV 进程、从磁盘恢复状态，**不是已验收的模型常驻服务**。跨轮状态连续不等于进程/权重常驻。
- 当前基础管线可运行，不代表摘要质量、固定槽位或状态融合已达到生产验收；生产真实事件的持续处理也需单独验收。

#### 状态如何输出：文本生成与专用编码不能混淆

RWKV 可直接从状态生成文本。输出“主题、约束、未完成、结果”等可读槽位，**不必先做投影或量化**；这是语义文本通道，仍然有压缩损失。

若要输出紧凑的专用记忆码，可以训练直接生成码符号的输出头，或采用“状态编码器 → 多个连续槽位 → RQ/FSQ 等量化 → 码符号”的路线。两者都需要验证，投影/量化不是唯一必经步骤。

关键限制：本地码本 ID、RWKV 词表 ID 与云端词表 ID 是三个不同对象。通过普通文本 API 发送 `<mem_017>` 会由云端重新分词，不等于注入一个专用 token。**只训练本地编码端，不会让未训练的云端自动理解这些码。** 固定位置保留协议结构，却不能自动赋予编码语义。

专用码需要可训练的下游 Transformer 或适用的云端微调接口；若以后支持输入 embedding/外部 KV，可改走连续前缀。RWKV 状态不是 Transformer KV，仍需训练跨模型映射，并匹配目标层、头、维度与位置机制。连续接口避免词表量化损失，但不保证无损，也不保证单个线性投影足够。

#### 下一步实验与训练路线

1. 构建经人工核对的小数据集：联合事件与四槽目标，覆盖否定、纠正、未执行计划、实体绑定、约束变更及未完成目标。划分训练/验证/测试，避免同会话或同模板泄漏。
2. 建立提示词基线及跨轮状态测试。评测格式合法率、槽位事实准确率、约束保持与虚报完成率；格式正确不等于记忆正确。
3. 选择支持 RWKV-7 反向传播的训练实现，再尝试 LoRA/适配头。当前 `rwkv` 推理包的 forward 包含 `no_grad`，不能直接接优化器就称为训练；输出头训练也不等于完整主干 LoRA。
4. 先在 GPU 跑 100–500 个真实训练 step，测显存、step 耗时与验证效果。8GB 上是否装得下取决于训练实现、序列长、批量与激活保存，推理显存不能推断训练显存。严禁 CPU 兜底。
5. 小规模可读槽位合格后再接云端。纯文本槽位用于当前商业 API；专用记忆码则先选定可训练下游模型，不能跳过消费端训练。
6. 专用码训练优先考虑后续预测/行为蒸馏损失与事实保持评测，而非只重建 S。比较“仅检索、检索+摘要、检索+槽位、检索+训练记忆码”；码数是实验变量，不预先保证几十或数百个就够。

**尚未开始实际训练；没有本机训练吞吐或完成时间实测。** 曾讨论的数小时至数天只属于粗略预算，不是承诺。Jamba/Zamba/Hymba 支持递归与 attention 互补的方向，但不能直接证明“本地 RWKV + 独立云端 API”跨模型状态编码有效。

### 1.4 一个常见误解：本地脑不是「小号的云端脑」

本地脑并不负责写记忆正文，它只写**流水**（`stream.md`）。
「把这一轮对话压成一条硬事实」这种活归云端脑 —— 原因在 §2.2。

### 1.5 「记忆跟代码走」的落法：私有主库 + 公开镜像

记忆是**私有资产**（含学号、真名、求职记录、角色卡），代码与文档是可分享的。
2026-10-13 起拆成两个仓库，**白名单就是硬边界**：

| 仓库 | 可见性 | 内容 |
|---|---|---|
| `TNong611/DBA` | **私有** | 全量：`memory/` + 代码 + 文档。**记忆的唯一版本化归处** |
| `TNong611/DBA-public` | **公开** | 只 `docs/ scripts/ port/ integrations/ README.md`，**不含 `memory/`** |

发布是一条命令，**先脱敏、再复查，复查不过就中止发布**（宁可不发，也不发出去）：

```bash
py -3.14 tools/publish_public.py --dry-run   # 只生成产物，不推送
py -3.14 tools/publish_public.py             # 白名单 → 脱敏 → 复查 → 推送
```

三条工程约束（都是踩出来的）：

- **脱敏清单本身不能进公开目录**：发布脚本刻意放在白名单之外的 `tools/`，
  否则「学号 → 占位符」的映射会把真值一起公开。
- **镜像目录的 `.git` 不能被清掉**：早先无条件 `rmtree(OUT)` → 残留半个坏 `.git`
  → `git add` 直接报 `not a git repository`。现在只清白名单内容 + `rev-parse` 自检。
- **镜像历史要接上远端**：重 init 出来的 root-commit 会被 non-fast-forward 拒；
  推送前先 `git fetch` + `git reset --soft FETCH_HEAD`。

⚠️ **写代码时的红线**：个人信息（学号/真名/公司名/API key）**不要写进 `scripts/`、`docs/`、`tools/`**
—— 它们会随公开镜像发出去；这类内容一律进 `memory/`。

## §2 三层记事本记忆

### 2.1 三层的职责、写入者与容量

| 层 | 文件 | 写入者 | 容量 | 消费方式 | 当前实测 |
|---|---|---|---|---|---|
| **核心记忆** | `memory/core.md` | **云端模型** | **≤ 15KB 硬限**（`CORE_MAX_KB = 15`） | **每轮全量注入**，不检索 | 15343B / 15360B（余 17B） |
| **记忆流** | `memory/stream.md` | **本地模型** | 不限（`STREAM_MAX_KB = 0`） | 仅检索，**一行一条「何时干过什么」** | 70415B（68.8KB） |
| **工作区册** | `memory/ws/<区>.md` | **云端模型** | 不限（`WS_MAX_KB = 0`） | 仅检索，存细节/结论/报错修法 | **14 册**，合计 330878B（323KB） |
| 向量层 | `memory/.vec/` | 构建脚本 | — | 语义检索通道，与关键词层零耦合 | **759 段** × 1024 维（bge-m3） |

写入者不是按「谁方便」分的，而是按**信息可得性**分的（见 2.2），
所以 `port/dba.py` 把它们做成三个不同名字的函数：
`remember_core` / `remember_ws`（云端模型用）、`remember_stream`（本地模型用）。
**这是故意的，不是笔误** —— 约束做成函数名，就不用靠人记文档。

### 2.2 为什么写入者必须分离

一句话：**提炼需要完整上下文，流水需要便宜且不间断。**

| 层 | 它要产出什么 | 这活需要什么 | 所以归谁 |
|---|---|---|---|
| `core.md` / `ws/*.md` | 一轮对话 → **一条硬事实 / 一段技术结论** | 看得见完整对话才能判断「哪句是结论」 | **云端模型**（它本身就在会话里） |
| `stream.md` | 一个时间点 → **一行「干过什么」** | 不需要判断质量，只需要**每轮都写、永不缺席** | **本地模型**（便宜、常驻） |

反过来说也成立：让昂贵的云端模型每轮写一行流水，是浪费；
让便宜的本地模型去提炼硬事实，它会写出一堆没有判断力的片段，把 15KB 的
核心记忆撑满而毫无价值。

顺带一条**内容边界**（写入侧的闸门保证）：`stream.md` 只记「事件」，
细节一律进 `ws/`。所以：

```text
# 对：一行一条，可被行级检索定位
- 2026-10-06 00:02:08 | tag=记忆系统 | 完成记事本三层记忆接管：拆掉旧五级注入链…

# 错：细节、代码块、表格 —— 它们属于 ws 册
```

### 2.3 容量策略为什么三层不同

**判断依据只有一条：这份内容每轮都要占 prompt 吗？**

| | 是否每轮进 prompt | 因此容量 |
|---|---|---|
| `core.md` | **是**，无条件全量 | **硬限 15KB，一个字节都不许猜**。超了就压缩，细则下沉到 ws |
| `stream.md` | 否，只在被检索命中时进 | 不限。**磁盘上可以无限长** |
| `ws/*.md` | 否，只在被检索命中时进 | 不限 |

注意「不限长」不等于「不限注入」：后两层虽然不限磁盘长度，
但检索侧另有预算 —— 单次检索命中总量上限 `RETRIEVAL_MAX_KB = 6`（6KB），
超了就触发二次检索（见 §2.5）。**磁盘无限，注入有限**，两件事分开管。

### 2.4 （重点）注入量随话题浮动，不随记忆总量增长

这是本架构与旧「五级记忆」**最根本的区别**，也是整个重构的动机。

**旧五级记忆**（USER → F0 → L3 → L2 → L1 按层权重组装）：每一层都有自己的配额，
**没命中的层也照样占预算**。于是注入量随记忆总量单调增长，最终撞上限：
记忆里留有一次真实事故的记录 —— 全量注入 `_assembled_context.md` 达到 154KB
（≈5 万+ token），直接导致整轮断流。后来给旧架构打的补丁是「预算制组装」
（36KB 预算），本质是在给一个错误的方向做限流。

**现在**的每轮注入只有两项：

```text
每轮注入 = core.md 全文（≤15KB，无条件）
         + 本轮检索命中（≤6KB，只有命中的段落才占字节）
```

于是：

| | 旧五级 | DBA 三层 |
|---|---|---|
| 注入量由什么决定 | **记忆总量**（分层配额之和） | **本轮话题**（命中了什么） |
| 记忆增长时 | 每轮越来越贵，直到撞上限 | 核心记忆不变，另两层长了也不进 prompt |
| 没命中的记忆 | 照样占预算 | **不占一个字节** |
| 上限的性质 | 需要靠预算算法维持 | 天然封顶：15KB + 6KB |

**用实测数字感受这个差别**：磁盘上三层记忆合计约 249KB
（core 14.0KB + stream 35.6KB + ws 198KB），而每轮注入上限约 21KB ——
比例已经超过 10:1，而且**这个比例只会继续拉大**，因为新增记忆落在
`stream`/`ws`，不落在 `core`。记忆从 249KB 涨到 1MB 时，每轮注入量**一个字节都不会变**。

这就是为什么 `stream.md` 和 `ws/*.md` 敢不限长度：它们的增长推高的是
**磁盘占用和检索耗时**，不是 **token 成本**。

### 2.5 检索侧的两条附加约束

**（1）`core.md` 默认不参与检索。** 它已经全量注入了，再被检索召回一次，
等于同一段内容占两份注入预算。所以 `nb_search.search()` 的默认行为是
**排除 `scope == "core"` 的文档**；确需检索时才显式 `--scope core`。
（文档仍然被索引，`collect_docs()` 里是 `add(C.CORE, "core", False)`。）

**（2）三级检索阶梯。** 第一级先按 BM25 取 `top_k` 段，**纯相关度，不掺时间权重**；
候选集必须可复现，否则「上次为什么召回不到」就无法排查：

```text
第一级：BM25 top_k，纯相关度
第二级：命中总量 > 6KB → 行窗口收窄 + 按「相关度 × 时间权重」重排
第三级：结果仍不清晰 → 放开 scope，再将 top_k 翻倍，最多放宽 2 次
```

第二级把命中段落切成行窗口，只保留「含查询词的行 ± 2 行」（`NARROW_WINDOW = 2`）。
时间权重使用语料中最新日期为参照点，公式为 `0.5 ** (距最新天数 / 30)`，半衰期 30 天，
下限 0.5；无日期段落取有日期段落权重的中位数（中性权重随记忆增长变化，不写死），
而不是 1.0。`time` 字段存在不等于权重生效：语料无日期或只跨 0 天时，所有权重均为 1.0，
排序与不加时间完全一致，必须如实报告「未生效」。

收窄判定**优先用 bigram**（长度 ≥ 2 的词），只有 bigram 一个都不中才退回单字 ——
旧实现直接拿全部词判命中，单字（「记」「忆」）把大量无关行拉进来，
收窄基本失效（实测 120 行全命中的文档，收窄后仍是 100% 体积），
而收窄失效正是「单条超预算压不回去」的直接原因。
退回单字这一级是**故意保留**的：查询本身就是单字时 bigram 为空集，只能靠单字。

**（3）诚实报告最终状态。** 命中量按分数丢弃到只剩一条时，
**它永远丢不掉**（`while len(hits) > 1` 循环退出），所以单条本身超预算的情形
必须单独处理，`RETRIEVAL_CLIP_OVERBUDGET_HIT = True` 时硬截断并在正文尾部
留下显眼的 `…（超预算已硬截断）` 标记。**唯一不允许的行为**是旧代码那种
「什么都没做，却在 note 里写『已二次检索收窄』」—— 实测 `max_bytes=1024`
时返回了 1154B，note 仍是那句假话。

### 2.6 核心记忆整理器：让 15KB 上限可自我维持

`core.md` 是唯一**每轮全量注入**的层，所以写满就是硬墙：2026-10-13 一度只剩 **15 字节**，
对话里任何新事实都塞不进去，只能先手工挤空间。整理这件事必须自动化，但**不能无条件信模型**
—— 它是减法，减错了就是永久丢事实。于是 `tools/curate_core.py` 做成三段式：

```text
① 模型提议    core.md + _pending_core.md（每日任务暂存的待并入条目）→ 重写全文
              默认 --engine deepseek（云端质量最高，单次几分钱）
              离线可选 --engine ollama（qwen3:8b 本地已装；15KB 中文很慢）
② 确定性校验  不看模型自述，只看产物：
              · 原始字节 ≤ 15360（不用 kb()：它把 15361 显示成 15.0KB，刚超限会静默通过）
              · 路径 / 反引号标识符 / DSH_*·nb_* 任务名 / 5 位端口 —— **四类 token 零丢失**
              · 分区（`## ` 标题）不丢、首行是 `# `
              · 字面 `{{` 不能变多（core 里本来就有一处是讲这条规则的）
③ 落盘        --apply：备份 core.md.bak-<时间戳> 后覆盖，并清空 _pending_core.md
              --auto ：仅在余量 <200B 时自动落盘（无人值守；平时只留提案，不无谓重写记忆）
              --verify 免调模型复验既有提案；--self-test 只测校验器本身
```

首次实战（2026-10-13）就拦下两次**真实损失** —— 闸门不是形式主义：

| 轮次 | 模型干的事 | 校验结果 |
|---|---|---|
| 1 | 把 `` `if cd.get("dated")` `` 这个代码片段改写成文字描述 | **拦下** → 补回原文后通过（15345 → 14146B） |
| 2 | 把 `port/dba.py`、`--self-test`、`collect_docs` 等 7 个标识符整段丢了 | **拦下**，拒绝覆盖 |

两条元教训（都已写进代码注释与任务书）：

- **校验器自己的提取器也会误拦**：`` ` `` 在 markdown 里会**跨行配对**，把整段文字当"标识符"；
  路径正则还会吞掉结尾反引号。改完必须跑 `--self-test`（每类各挑一个**真实存在**的 token 删掉，必须被拦）。
- **禁止手工搬提案**（`_pending_core.curated.md` → `core.md`）：那等于绕过闸门。
  当天手工搬过一次，把没验过的提案变成记忆，靠 `core.md.bak-*` 才救回来。

调度：`DSH_Memory_Curate` 每日 **00:20**（紧接 00:05 的维护任务）；
子代理任务书 `integrations/dsh/curator-agent.md`（固定流程 + 禁止事项）。

## §3 向量层

### 3.1 关键词通道的天花板：它只能精确匹配

关键词索引（`memory/.index/inverted.json`，CJK 二元组 + BM25）的本质是
**token 精确匹配**。查「记忆架构」只能命中含这些字及其二元组的段落。

它的强项是：精准、可解释、**纯标准库零依赖**、单机毫秒级。
它的弱项是**同义改写**：

```text
查「怎么让模型记住我」
  → 关键词通道：查不到（目标段落里没有这几个字）
  → 向量通道：查得到（语义上就是「记忆连续性方案」）
```

这类查询在真实使用里不是边角情况 —— 用户不会记得自己当初把这件事命名成了什么。
所以另建一层向量索引（bge-m3，1024 维，走 Ollama GPU）。
两者是**互补关系，不是替代关系**：向量擅长语义召回，但会给出「很像但不对」的段落；
关键词可能漏掉改写的问法，但一旦命中就几乎不会错。

### 3.2 为什么与关键词层【零耦合】

这是**可靠性要求，不是洁癖**：

| | 关键词层 | 向量层 |
|---|---|---|
| 依赖 | Python 标准库 | Ollama 进程 + 模型 + **GPU** |
| 挂了会怎样 | 代码/索引真坏了 | 很常见（服务没起、GPU 被占、模型没拉） |
| 恢复成本 | 重建索引 | 起服务、拉模型、等 GPU |

如果用一个入口把两者串起来，**Ollama 一挂就等于整个记忆检索全哑** ——
连本来完全可用的精确检索也没了。现在的做法是两条通道各自独立建索引、
独立检索、各自可单独工作：

```python
r = dba.recall("怎么让模型记住我", mode="auto")   # 关键词优先，命中不足再补向量
r = dba.recall("记忆系统",        mode="kw")     # 只走关键词（不需要 Ollama/GPU）
r = dba.recall("记忆系统",        mode="vec")    # 只走向量
r = dba.recall("记忆系统",        mode="both")   # 两条都跑，按排名交错合并
```

**降级必须明确报告。** 返回值里永远有 `degraded` 字段说明哪条通道没跑：

```python
{"query": ..., "hits": [...], "channels": ["kw","vec"],
 "degraded": ["vec:VecUnavailable: 连不上 Ollama（http://127.0.0.1:11434）…"], ...}
```

静默降级在本项目里已造成过**实际损失**：使用者以为「语义检索也说没记过」，
于是重复问同一件事，或者以为记忆丢了。所以宁可返回一条带刺的记录，
也不返回一份看起来正常的结果。

**两条通道的分数不可比**，因此 `mode="both"` 的合并是**按各自排名交错取**
（`port/dba.py::_merge`），**不做分数相加**：

- 不做**拼接**：关键词通道每次都能返回满 top_k，拼接会把名额全占掉，
  向量通道的语义命中永远看不到。
- 不做**相加**：BM25 分数与余弦相似度量纲不同，直接相加排序会让某一通道
  凭量纲优势吃掉全部名额。
- 必须**去重**：同一段很可能两条通道都召回，不去重的话 top_k 被同段的副本占满，
  看起来命中很多、信息量却没增加。

另外两条索引的**切分单元必须一致**（向量层直接复用
`nb_index.collect_docs()`），否则同一个问题在两边命中不同粒度的段落，
合并时必然重复或缺漏。

### 3.3 余弦用绝对阈值，BM25 用相对归一

两个通道的阈值逻辑**刻意不同**，照搬会出假结果：

| | BM25（关键词） | 余弦（向量） |
|---|---|---|
| 分数量纲 | **浮动**：随 idf、文档长度、语料整体平移 | **有物理意义**：同语言相关段落 > 0.6，不相关 < 0.4 |
| 实测区间 | 同一份语料里中位数 1.6~5.8、最大值 2.0~23.4；换语料整体平移 | [−1, 1]，且被 L2 归一后就是点积 |
| 阈值形式 | **相对本次最高分归一**：`RETRIEVAL_MIN_SCORE_RATIO = 0.0`（0.0 = 关闭） | **绝对值**：`VEC_MIN_SCORE = 0.45` |
| 为什么 | 写死的绝对分早晚不是变成空操作就是误杀 | 把 BM25 那套归一照搬过来，会得到「用最高分 0.3 的垃圾当满分」 |

第 4 行是关键：如果对余弦也做「按本次 top 归一」，那么一次查询里
**最不像的那一段也会被当成 1.0 分命中** —— 因为归一化的定义就是让最高分变成满分。
向量检索的价值恰恰在于「没有近邻时应该返回空」，归一化会把这件事抹掉。

反过来，BM25 侧写死的绝对阈值 `RETRIEVAL_MIN_SCORE = 0.8` 实测是**空操作**：
13 个真实查询（含「的」「机」「表」这类极泛词），top-5 候选**无一低于 0.8**，
阈值真正起作用的查询 = **0/13**，低于 0.8 的候选只占总候选的 0~11%
且全部落在 top-5 之外 —— 既不滤垃圾也不拦有用结果，白占一行配置。

> ⚠️ **常量改名为 `RETRIEVAL_MIN_SCORE_RATIO` 是故意的。**
> 如果沿用旧名，某个旧脚本或旧配置里残留的 `0.8` 会被悄悄解释成
> 「最高分的 80%」= 激进过滤，**静默改变检索结果**。
> 改名让残留引用直接 `AttributeError`，而不是默默变脸。
> 同理旧名**不保留**为 `0.0` 别名 —— 那等于允许旧值继续生效。

### 3.4 GPU 是硬要求，不做 CPU 兜底

向量层**不做**「GPU 不可用就退回 CPU」的兜底。理由不是性能洁癖：

> 兜底会让一条**慢到不可用**的路径悄悄生效，而人还以为在用 GPU。

拿不到 GPU 就直接报错（`VecUnavailable`），让人看见。`nb_vec.gpu_status()`
读 Ollama `/api/ps` 的 `size_vram / size` 把实际算力分布打出来，
就是为了让「悄悄退到 CPU」这件事有地方暴露。

### 3.5 存储格式与原子性

```text
memory/.vec/vectors.npy   float32 [N, 1024]，已 L2 归一化（之后点积即余弦）
memory/.vec/meta.json     {"model","dim","count","built","elapsed_s","items":[…]}
                          items[i] = {id, file, scope, title, head, text}
```

两个文件**必须同时写入且行数一致**。写入用「先写 `.tmp` 再原子 `replace`」，
读取时校验 `count == 行数`、`dim` 一致、`items` 非空，**任何不符直接判损坏**。

其中**最危险的半写状态是「npy 换了、meta 没换」**：行与元数据错位后，
检索会返回**内容对不上的段落** —— 这比直接报错危险得多。所以行数不一致
必须硬失败，不能「尽力而为」。

> ⚠️ **踩过的坑**：临时文件不能写成 `vectors.npy.tmp`。
> `np.save()` 见到路径末尾不是 `.npy` 会**自动补上 `.npy`**，
> 文件实际落在 `vectors.npy.tmp.npy`，而 `replace` 找的是 `vectors.npy.tmp`
> → `FileNotFoundError`（2026-10-06 实测）。临时名必须自己以 `.npy` 结尾。

## §4 注入分两段与前缀缓存

### 4.1 划分依据是「变化频率」，不是「重要性」

组装产物被拆成两个文件、两个 prompt section：

| 段 | 文件 | 变化频率 | 注入位置 | 落地实现 |
|---|---|---|---|---|
| 稳定段 | `memory/_core_context.md` | **几天才变一次**（核心记忆） | prompt **前部** | DSH：`order = -50`（在 persona 之前） |
| 变化段 | `memory/_hits_context.md` | **每轮都变**（检索命中） | prompt **最末尾** | DSH：`order = 200`（在工具定义 `150` 之后） |

另有 `memory/_assembled_context.md` 是两段的拼接，**保留给仍按单文件消费的调用方**
（旧接入点的协议不变）。新接入方应当读两个文件、分别注入。

### 4.2 合一段会怎样：92.7% → 0%

前缀缓存的前提是「**前缀**完全一致」。把两段合成一个 section 之后，
检索一旦命中，system prompt 从**该 section 起**整段变化 ——
其后所有段落（工具定义、人格段）的缓存全部失效。

> **实测差距：命中率 92.7% → 0%。**
> 反向也验证过：变化内容（时间戳）进前缀 → 命中率 0%；
> 稳定在前、变化在后 → 92.7%。

所以这不只是「省 token」的优化，它直接决定每轮的成本量级。

### 4.3 落地细节清单（每一条都对应一次实际失效）

1. **首行时间戳注释必须在注入时被剥掉。**
   `nb_assemble` 在 `_core_context.md` 第一行写了
   `<!-- Notebook core | built: <时间戳> | …KB/15KB -->`，
   DSH 侧用 `BUILT_LINE_RE` 专门匹配并删除它。
   剥不掉的话，每轮变化的时间戳就留在正文里 → **前缀缓存全失效**。
   ⚠️ 因此**第一行的格式不许动**，所有告警只能加在它**之后**。
   三种历史前缀（`SnowFox Memory Assembly` / `Notebook Memory` / `Notebook core`）
   都要认 —— 曾只匹配旧前缀，迁移后时间戳留在正文里，缓存再次全失效。
2. **核心记忆段在会话内做快照缓存。** 同一会话只读一次并固定下来，
   会话中途重建核心记忆不影响已固定的前缀（命中率从 53% 回到 90%+）。
   刷新时机是 `session/created` 事件。
3. **检索命中段绝不缓存。** 它本来就该随本轮输入变化，缓存住就等于永远检索不到新东西。
   它排在末尾，变化也不破坏前缀。
4. **`{{` 必须被打断**（见 §5.5 与 §8）：正文里的角色卡占位符会让插值器
   遇到未注册变量而**整轮抛错**。修法是在生成端
   （`nb_assemble.escape_braces`）把每个 `{` 之后插入零宽空格 `\u200b`，
   **不是**在注入端注册「字面量变量」—— 那等于永久关闭 DSH 的未知变量校验器，
   任何一次真正的变量拼错都会被静默放过。
5. **注入总量有硬闸门。** DSH 侧 `snowfox-inject.mjs` 的 `MAX_BYTES = 64KB`
   超限处理**不是截断**，而是 `readSection()` 直接 `return ''` ——
   记忆会在**没有任何报错**的情况下整体消失，人和模型都只会觉得「这轮没想起什么」。
   所以 Python 侧用 `INJECT_HARD_LIMIT_B = 64 * 1024` 镜像一份，
   到 `ASSEMBLY_WARN_RATIO = 0.75`（48KB）就告警，并把告警**渲染进 core 段正文**
   （对模型可见）+ 打到 stderr（对人和 cron 日志可见）。

> ⚠️ **两个上限性质不同，不要互相替代**：
> `CORE_MAX_KB = 15` 是**每轮成本**约束（用户定的硬数值，一个字节都不许猜）；
> `INJECT_HARD_LIMIT_B = 64KB` 是**下游会丢内容的闸门**。
> 15KB 的 core 离 64KB 看着很远，但命中段随时能再吃掉几 KB ——
> 所以算「下界」时必须把 core 和固定开销一起算进同一个 64KB 里
> （`ASSEMBLY_OVERHEAD_B = 400`，实测约 400B 的非正文开销）。

## §5 哨兵值纪律

> 这一节写得重，因为它是本项目**反复踩、已经踩过至少四次**的坑。
> 如果这份文档只能保留一节，保留这一节。

### 5.1 原则

> **「失败 / 无值」与「真实取值」绝不能共用同一个返回通道。**
>
> 否则失败会被当成一个**合法的取值**静默吃掉 —— 不抛错、不告警、不写日志，
> 数据就这么没了。而「静默」比「报错」危险得多：报错会被立刻看见，
> 静默只会让人以为系统正常、以为记忆真的没有。

判断自己有没有踩坑，问一个句子就够：

> **调用方拿到这个返回值，能不能区分「操作失败」和「操作成功且值就是这个」？**

只要答案是否，就是同一个病。

### 5.2 四个真实事故

| # | 位置 | 错误做法 | 实际后果 |
|---|---|---|---|
| 1 | `nb_migrate.date_of()` | 无匹配时返回哨兵字符串 `'未标日期'`，而不是空串 | 调用方 `if h_date:` **恒为真**：某个真日期容器读到的 `'未标日期'` 被当成有效日期写进 `last_date`，然后把后续所有块的日期覆盖掉 —— **96 条记录只剩 1 条带着真日期** |
| 2 | `nb_index.load()` | 用 `None` **同时**表示「索引不存在」和「索引 JSON 损坏」 | 调用方无法区分，一律报「索引不存在，请先运行 nb_index.py」——**而文件其实存在**，提示是假的。更糟的是 `nb_bridge.index_stale()` 只看 `exists()+mtime`，一份写坏的索引被判「**新鲜**」，永不重建 → **检索永久静默返回 0 命中**，且与「真的没命中」不可区分 |
| 3 | `nb_config.kb()` | 返回值 `0.0` **同时**表示「文件不存在」和「文件存在但为 0 字节」 | `core.md` 被删后组装头部平静地显示 `core=0.0KB/15KB`，与「核心记忆真的为空」**完全同形**；而且 `0.0 > CORE_MAX_KB` 恒为 `False`，**超限告警连带静默失效**。而 core 是每轮全量注入项，它没了等于记忆全哑，下游读不到文件也只是 `return ''` |
| 4 | `nb_write.reindex()` | `return (r.stdout or r.stderr or "").strip()…` —— **成功与崩溃共用同一个返回通道**，且从不检查 `r.returncode` | `nb_index.py` 崩了就把 stderr 最后一行当成正常摘要返回，调用方/用户看到一行文本，**以为索引建好了** —— 而索引其实是旧的，检索静默漏掉刚写入的内容 |

四个事故的共同结构：

```text
失败  ──┐
        ├──→ 同一个返回值 / 同一个通道 ──→ 调用方无法区分 ──→ 静默错误行为
真实值 ──┘
```

### 5.3 现在怎么做：不同故障走不同通道

用**各自独立的类型**，把每类故障做成可区分的信号：

| 信号 | 类型 | 语义 | 调用方该做什么 |
|---|---|---|---|
| `MISSING` | `nb_config.MissingSize(float)`（值 `-1.0`，带 `.missing = True`） | 「文件不存在 / 读不到」 | 报显眼错误态，**不是**当成 0 字节 |
| `IndexCorrupt` | `nb_index.IndexCorrupt(Exception)` | 索引存在但不可用（JSON 坏 / 缺字段 / `docs` 为空） | 重建；并且**要知道它坏过** |
| `VecCorrupt` | `nb_vec.VecCorrupt(RuntimeError)` | 向量索引损坏（npy 与 meta 不一致 / 维度不符 / JSON 坏） | 重建；说明上次写入被打断了 |
| `VecUnavailable` | `nb_vec.VecUnavailable(RuntimeError)` | 环境不可用（Ollama 没起 / 模型没拉 / 拿不到 GPU） | 报降级，但**关键词通道照常返回** |

几个设计细节值得单独记住：

- **`MissingSize` 取 `-1.0` 而不是 `NaN`**：真实文件大小恒 ≥ 0，负值不可能是测量结果；
  且 `f"{-1.0:.1f}KB"` 渲染成 `-1.0KB` 在日志里一眼可疑，而 `NaN` 会渲染成 `nanKB`
  并让 JSON 产出非法的 `NaN` 字面量。
- **`MissingSize.__format__` 被重写**成返回 `缺失!core.md不存在`，这是**零改动放大**的关键：
  调用方原本拿 `kb()` 的返回值直接拼进文案（如 `{core_size_kb()}KB/{CORE_MAX_KB}KB`），
  若只返回 `-1.0` 仍像个数字，读的人容易当成测量结果。重写 `__format__` 后，
  **所有既有插值点自动变成错误态文案**，不需要逐个去改调用方。
  另外还提供 `is_missing(path)` / `kb_label(path)` 供显式区分「缺失」与「0 字节」。
- **`load()` / `load_or_none()` 并存**：需要区分时用 `load()`（损坏抛异常），
  确实「拿不到就当没有」的场景才用 `load_or_none()`（两种都返回 `None`）——
  后者是**显式的让步**，写在函数名里，而不是让默认行为含糊。
- **布尔比较也必须先判缺失**。`nb_assemble.core_over_limit()` 里：

  ```python
  # 旧写法：return core_size_kb() > C.CORE_MAX_KB
  # → kb() 对不存在返回 -1.0，而 `-1.0 > 15` 恒为 False → 静默通过
  if core_missing():
      return True                     # 缺失一律算异常态：宁可误报也不许静默
  return core_size_kb() > C.CORE_MAX_KB
  ```

  这是同一个病在**调用侧**的残留：`nb_config` 已经把「缺失」和「0 字节」分开了，
  但布尔比较又把区别抹平了。修复后「缺失」与「超限」在组装正文里是**两条独立告警** ——
  它们的排查方向完全不同（一个是去找文件，一个是去压缩），文案混用会把排查者
  引向「去压缩一个并不存在的超限」。
- **写入侧同样分道**：`nb_write` 用退出码区分三种结果 ——
  `0` 成功 ｜ `1` 参数非法/内容为空（**一个字节都没写**）｜
  `2` 内容已写但索引重建失败（检索暂时看不到这次写入，**不要重写内容**，
  重写会在记忆流里留下两条重复记录）。
- **`--at` 不传 ≠ 传空串**：`None`（没传）才用当前时间；空串报错。
  旧写法 `at or time.strftime(...)` 会把空串静默变成**一个假的当前时间戳**，
  而排序和检索正是按时间戳定位的 —— 假时间戳比空值更难查。
  同理 `ws` 的 `area` 为空必须报错，**不做** `or "misc"` 兜底：
  兜底会让「调用方少传参数」和「真的叫 misc」两条来源糊进同一个 `misc.md`，事后分不开。
- **非法输入不许「静默变成另一个合法名字」**：旧 `safe_area` 会把
  `a/b`、`a:b` 里的非法字符**静默删掉**变成 `ab`，与本来就合法的 `ab` 撞进同一个文件 ——
  两个不同项目的工作区互相覆盖且没有任何提示。现在一律报错，并带上被拒的字符。

### 5.4 诚实说：现在也还有残留

同一类错误**还会再犯**，因为它的形态每次都不一样。写文档时已知的两处残留：

1. **`port/dba.py::recall(mode="auto")` 关键词侧失败不上报。**
   该分支只收集了向量侧的错误：

   ```python
   degraded = []
   if vec.get("error"):
       degraded.append(f"vec:{vec['error']}")     # kw 的 error 在这一支里被丢掉了
   ```

   也就是说 auto 模式下关键词通道自身报错时，结果仍然声称 `channels=["kw","vec"]`
   而 `degraded` 为空。`recall_both()` / `_kw_only()` 本身是对的，问题只在 auto 这条路径。
2. **向量通道不排除 `core`。** 关键词侧默认排除 `core`（避免与全量注入重复占预算），
   但 `nb_vec.collect_items()` 直接复用 `collect_docs()`，`nb_vec.search()` 也不排除 ——
   同一个 core 段可能既被全量注入、又被向量召回一次。当前 508 段中有 7 段来自 core，
   影响有限，但策略两边不一致，属于待对齐项。

写在这里而不是悄悄改掉，是因为**「知道还有残留」和「以为已经干净了」是两种完全不同的状态**。

### 5.5 以后写代码时的检查清单

1. 这个返回值，调用方能区分「失败」和「成功的这个值」吗？
2. 我有没有用某个**合法取值**（`0`、`0.0`、`None`、`""`、`'未标日期'`）去表示失败？
3. 我是不是在**同一个通道**里同时输出成功和错误（stdout-or-stderr、返回值-or-异常）？
4. 布尔比较、长度判断、格式化的地方，**失败态会不会被抹平**成普通值？
5. 失败时我有没有**说出去**（异常 / 显式字段 / 日志 / 正文告警），还是静默降级？
6. 参数默认值能不能区分「没传」与「传了空值」？
7. 我改了一个常量的**含义**（不只是数值）时，改名了没有？
8. 一句话：**这条路径失败时，最坏情况下会不会有人以为它成功了？**

## §6 已知限制与未做完的事

诚实列出，不粉饰。每一条都写了「为什么现在是这样」和「代价是什么」。

### 6.1 每轮组装是**同步**子进程调用（约 100ms）

宿主在用户输入到达时**同步**调用 `nb_bridge.py` 并等待它写完
`_core_context.md` / `_hits_context.md`。

- **为什么不异步**：紧接着的 prompt assembly 就会读这两个文件，
  异步重建存在**竞态** —— 读到的可能是上一轮的命中，而且这种错误**完全静默**
  （看起来像「检索没命中」）。
- **代价**：用户输入到模型开始推理之间多了一次串行等待，实测重建 ~100ms
  （含冷启动建索引 ~200ms），相对 LLM 往返可忽略。子进程超时设 15s。
- **已知不完善**：组装失败只写日志、不影响会话（设计如此），
  但这也意味着**组装连续失败时用户不会被打断**，只会觉得「记忆最近不太好用」。

### 6.2 向量索引是**全量重建**，没有增量更新

`nb_vec.build()` 每次都把 `collect_docs()` 的全部段落重新嵌入一遍。
当前 508 段、1024 维，`meta.json` 里记录的构建耗时 **11.5s**（约 12s），
`vectors.npy` 2080896B，`meta.json` 337011B。

- **代价**：写完一条记忆后想立刻用向量检索，要么等十几秒全量重建，
  要么接受索引陈旧。真实使用里靠 `stale()`（数据文件 mtime 比索引新就报陈旧）
  提示，而不是自动重建。
- **没做**：增量追加 / 段落级失效（只重算变动的段）。**没做的原因**是
  断点在这：全量重建的正确性已经验证过，增量会引入「npy 与 meta 部分更新」
  这类更难发现的不一致（正是 §3.5 里最危险的那类半写状态）。
- **2026-10-13 追加：Ollama 大批量嵌入是「挂死」而不是报错。** 单请求 token 总量过大时
  （旧实现 `batch=16` × 每条 4000 字符 ≈ 3 万 token，而 bge-m3 上限才 8192），
  `/api/embed` 客户端超时后**服务端还在算**，后续请求全部排队超时 —— 通道看起来"死了"，
  单独打一次又会 0.8s 返回，极易误判成"模型太大"。实测：1 条 4000 字符 ✅ 0.3s；
  4 条各 4000 字符 ❌ 挂死 75s+；16 条**短**文本（合计约 1200 字符）✅ 0.1~1.5s
  —— **瓶颈是字符总量，不是条数**。
  现在：`build(char_budget=1800)` 按**字符预算**分组 + 90s 快速失败（错误里直接给重启命令）；
  中断可续：`tools/vec_rebuild_resilient.py`（分块 + 检查点 + 卡死自动重启 Ollama，
  实测 758 段 / 12 秒 / **0 次重启**）。

### 6.3 中文分词是自建的 CJK 二元组

`nb_index.tokenize()`：CJK 连续串 → **一元 + 二元**；ASCII 字母数字串 → 整词（长度 ≥ 2）。

- **为什么不用 SQLite FTS5 的 `trigram` 分词器**：它是 3 字符滑窗，
  **2 字中文词永远匹配不到**。实测：`五级` → **0 命中**，`五级记` → **1 命中**。
  中文里 2 字词占比极高，所以 trigram 不可用。
- **为什么不用 jieba / sklearn**：本机没装；而且关键词层的价值之一就是
  **纯标准库零依赖**（Ollama 挂了它还能跑，见 §3.2）。
- **代价**：一元词会带来噪声，靠 BM25 的 idf 自动降权（高频一元词 idf 低），
  没有手工加权。词形变化（「记忆」vs「记忆的」）不归一，靠二元组覆盖。
  索引体积也因此偏大：508 段文档的 `inverted.json` 是 **1837725B（约 1.8MB）**，
  比记忆正文本身还大 —— 这是「零依赖 + 二元组展开 + JSON 明文」的直接代价。

### 6.4 记忆流的写入闸门是**启发式规则**，宁可漏过也不错杀

`nb_write._STREAM_JUNK` 用正则拒收：对话残片（`5.5呢？ 测完了`）、
系统报错（`Hermes hit repeated errors…`）、`ok/好的/收到` 这类空话、
裸链接与裸密钥、以及 < 8 字符的碎片。

- **为什么是启发式**：判定要**窄**。错杀一条真实工作记录，是**永久的数据损失**；
  漏过一条垃圾，只是占掉一个检索名额（检索是 top_k 截断的，代价有限）。
  两者不对称，所以规则宁松勿严。
- **代价**：垃圾还会进。已知漏网形态主要是「有信息量但形态像对话」的条目，
  以及长度超过阈值但内容是提问而非动作的行。
- **配套约定**：要记细节请用 `ws`（工作区册不限长度、就是用来存细节的），
  **别往记忆流塞细节** —— 它的价值在「一行一条、可被检索定位」。

| `tools/` | 运维工具：`curate_core.py` / `publish_public.py` / `vec_rebuild_resilient.py` | 刻意**不在公开镜像白名单内**（见 §1.5） |
| `training/` | RWKV 槽位解码实验产物 | 不进公开镜像 |
| `backups/` | 迁移前备份 | — |

### 7.2 数据流 A：每轮组装（注入）

```text
用户输入
  │
  ├─ DSH 插件 snowfox-sync.mjs（user/message 事件）
  │     └─ execFileSync: py -3.14 nb_bridge.py      ← 用户输入走 stdin（免 shell 转义）
  │           ├─ query 来源：显式参数 → memory/.query → 退回「核心记忆里的活跃待办」
  │           ├─ ensure_index()：索引不存在 / 损坏 / 任意数据文件比索引新 → nb_index.build()
  │           ├─ nb_assemble.write_assembly(query)
  │           │     ├─ 读 core.md 全文（+ 缺失/超限告警）→ _core_context.md   稳定段
  │           │     ├─ nb_search.search_ladder(query)：阶梯三级（阶梯模式下）
  │           │     │     ①BM25 top_k（纯相关度，候选集可复现）
  │           │     │     ②命中 >6KB → 行窗口收窄 + 按 相关度×时间权重 重排
  │           │     │     ③仍不清晰 → 放开 scope / top_k 翻倍（≤2 次，如实报 relaxed）
  │           │     │     ⚠️ 纯数字片段（`2023`→`202301230000`）走**有闸门**的子串扩展：
  │           │     │        仅当精确词一个候选都没有时才启用，避免污染精确排名
  │           │     │     → _hits_context.md         变化段
  │           │     ├─ 两段拼接 → _assembled_context.md（兼容老调用方）
  │           │     ├─ escape_braces()：每个 { 后插零宽空格
  │           │     └─ 预算检查（64KB 硬上限 / 48KB 告警）→ 写进 core 段正文 + stderr
  │           └─ 输出一行摘要：index=… bytes=… core=…KB hits=… query=…
  │
  ├─ 云端模型收到三样东西：核心记忆全量 + 本轮命中 + 用户输入
  │     └─ 记忆不清晰时**可主动二次检索**（设计内的）：
  │        py -3.14 nb_search.py "关键词" --top-k N   ／   py -3.14 nb_vec.py query "关键词"
  │
  └─ DSH 插件 snowfox-inject.mjs（prompt assembly 时）
        ├─ order -50：_core_context.md（剥掉首行时间戳注释；会话内快照缓存）
        └─ order 200：_hits_context.md（每轮重读，**不缓存**）
```

### 7.3 数据流 B：写入（按写入者分口）

```text
云端模型（在会话里，看得见完整上下文）
  ├─ py -3.14 nb_write.py core "硬事实" --title 路径        → core.md   （追加到同名段/新建段）
  │    py -3.14 nb_write.py core --file new_core.md         → core.md   （整体覆盖；与 --append 互斥）
  │    └─ ⚠️ 缩水闸门：新内容 < 旧内容一半时**拒绝写入**，core.md 一个字节不动
  │          （`--file` 极易被当成追加用；2026-10-11 实测把 15331B 换成 716B 且退出码 0）
  │          确实要整篇重写 → 加 `--force`。空源文件另判，一律拒。
  └─ py -3.14 nb_write.py ws 双脑Agent "细节/结论/修法" --title X → ws/双脑Agent.md
          │
          └─ 两者收尾都会自动 reindex()（关键词索引全量重建，毫秒级）
                 失败 → 退出码 2：**内容已写入**，只是索引没更新（不要重写内容）

本地脑 / 宿主插件（每 turn 结束）
  └─ snowfox-sync.mjs appendEvent()：一行直接 append 到 stream.md
       （只记 source.kind === 'user' 的人类输入 → 取助手回复压成单行，上限 90 字符）
       └─ 防抖 20s 后 spawn nb_index.py 重建关键词索引（避免每轮全量重建）
```

三个子命令的**内容边界**（写错地方就白写了）：

| 子命令 | 写什么 | 例子 |
|---|---|---|
| `stream` | 「**何时干过什么**」，一句话一条，不写细节 | `完成记事本三层记忆接管：拆掉旧五级注入链…` |
| `core` | 硬事实 / 约束 / 偏好 / 待办 / 反复踩的坑 | 路径、配置值、代理地址 |
| `ws` | 某工作区的细节、结论、报错与修法 | 一段技术方案、一次故障的修法 |

### 7.4 数据流 C：重建索引

```text
关键词索引（纯 Python，毫秒级，不需要 GPU）
  py -3.14 nb_index.py                 # 全量重建
      collect_docs()  ── core（按 ## 段）/ stream（**按行**）/ ws（按 ## 段）
      tokenize()      ── CJK 一元+二元，ASCII 整词
      BM25 参数       ── K1 = 1.5, B = 0.75
      → memory/.index/inverted.json
  触发时机：① 每次 nb_write 写入后自动；② nb_bridge.ensure_index() 发现陈旧/损坏；
            ③ 宿主插件防抖 20s；④ 人工 py -3.14 nb_write.py reindex

向量索引（需 Ollama + bge-m3 + GPU，全量重建约 12s）
  py -3.14 nb_vec.py build             # 见 §6.2：**目前只有全量**
      collect_items() ── 复用 nb_index.collect_docs()（两层切分单元必须一致）
      embed_text_of() ── 标题 + 正文，截断 4000 字符（超长段落尾部是噪声）
      _embed()        ── POST /api/embed 批量 16 条一次
      L2 归一化        ── 之后余弦退化为点积
      → 先写 vectors.tmp.npy / meta.tmp.json，再原子 replace 两个正式文件
  触发时机：人工；或按计划任务。**不自动**（写入后不会顺手重建向量）
```

> ⚠️ 记忆流的切分单元是**按行**（`parse_lines`），工作区册是**按段**（`parse_sections`）。
> 这不是随意选的：`stream.md` 全是单行 bullet、没有 `## ` 标题，
> 按段切会把**整个文件变成一个巨型检索单元** —— 实测（2026-10-05 冒烟）
> 所有查询都命中同一个 `(前言)`，检索等于失效。

## §8 踩坑速查表

按主题分组，方便以后遇到相似症状时直接对号入座。**每一条都是真实发生过的。**

### 8.1 静默失败 / 哨兵值（详见 §5）

| 症状 | 根因 | 修法 |
|---|---|---|
| 大量记录缺字段 | 哨兵值 `'未标日期'` 与真实值同通道，`if x:` 恒真 | 无匹配返回**空串** |
| 索引坏了却报「索引不存在」，且永不重建 | `None` 同时表示「不存在」和「损坏」 | `IndexCorrupt` 独立异常 |
| `core.md` 被删后无任何告警 | `0.0` 同时表示「不存在」和「0 字节」，`0.0 > 15` 恒 False | `MissingSize(-1.0)` + 重写 `__format__` + 先判缺失 |
| 子进程崩溃被当成建索引成功 | `stdout or stderr` 共用返回通道，从不看 `returncode` | 失败抛 `IndexRebuildFailed`，退出码 0/1/2 分档 |
| 组装的 `note` 说的和实际不一样 | 只描述**初始**状态或**声称**了没做的事 | 描述**最终**状态；没收窄就别说收窄 |
| 空 `--at` 变成假时间戳 | `at or now` 把空串当没传 | `None` 与 `""` 两条通道，空串报错 |
| 两个项目的工作区互相覆盖 | 非法字符被静默删除（`a/b` → `ab`），撞名 | 非法字符报错，并列出被拒字符 |

### 8.2 检索与索引

| 症状 | 根因 | 修法 |
|---|---|---|
| 所有查询都命中同一段 | 无 `## ` 标题的文件被按**段**切，整文件变一个巨型单元 | 记忆流**按行**切（`parse_lines`） |
| 双字中文词永远查不到 | FTS5 `trigram` 是 3 字符滑窗（`五级` → 0 命中） | 自建 CJK 一元+二元倒排 |
| 阈值配置形同虚设 | 写死绝对 BM25 分数 0.8 → 13 个真实查询 0/13 生效 | 改为**相对最高分**归一；且**改名**避免旧值被误解 |
| 二次检索收了窄却还是超预算 | 收窄用单字判命中 → 行行命中 → 收窄率 100% | 优先 bigram，bigram 全不中才退回单字 |
| `--scope core` 几乎总是 0 命中 | 先按全库 top_k 截断再过滤（core 全库排名 11~103） | **先过滤、再截断**，写成两段独立代码 |
| 纯数字查询静默返回空 | 位置参数末位是数字就被当成 `top_k` | 只认 `--top-k N`；缺值报错而非退回默认 |
| `--scope` 漏值静默变「查全库」 | `scope = args[i+1]` 越界后未校验 | 缺值直接报错退出 |
| 返回内容对不上的段落 | 向量 npy 与 meta 半写错位 | 校验行数一致，不符即 `VecCorrupt` |
| `np.save` 后 `replace` 报文件不存在 | `np.save` 给非 `.npy` 结尾的路径自动补 `.npy` | 临时名自己以 `.npy` 结尾 |
| 向量重建报「嵌入超时」，但单独打 `/api/embed` 秒回 | 单请求过载把 Ollama **挂住**（客户端超时后它还在算，后续全部排队） | 按字符预算分组 + 90s 快速失败 + 重启 Ollama；见 §6.2 |

### 8.3 注入与 prompt

| 症状 | 根因 | 修法 |
|---|---|---|
| 前缀缓存命中率 0% | 变化内容（时间戳 / 检索命中）进了 prompt 前部 | 稳定段在前（`-50`）、变化段在**最末尾**（`200`）；首行时间戳注入时剥掉 |
| 记忆整段凭空消失且不报错 | 下游 64KB 是 `return ''` 而不是截断 | Python 侧镜像 64KB + 48KB 告警，写进正文与 stderr |
| 某一轮直接抛错失败 | 正文里的 `{{char}}` 被插值器当未注册变量 | 生成端把**每个** `{` 后插零宽空格；**不**注册字面量变量（那会关闭校验器） |
| 残留裸 `{{` 仍然抛错 | `str.replace("{{", …)` 是单次不重叠扫描，奇数个 `{` 会漏（`{{{char}}}` → 残留） | 逐字符插入零宽字符，n=2..8 全覆盖 |

### 8.4 迁移（五级 → 三层）

| 症状 | 根因 | 修法 |
|---|---|---|
| 43.7KB `recent.md` + 96KB `summary.md` 整份消失 | 标题形如 `## 2026-10-04 15:53:01 \| session=… \| 纪要`，被 `is_meta()` 判为容器而连正文一起 `continue` | 容器判定**只看有没有正文**：只有空正文的纯日期标题才是容器 |
| 78 个块全被染成同一天 | 「任何带日期的标题都更新 `last_date`」，而 `long_term.md` 的日期标题**带正文**，是内容块不是容器 | 只有**空正文**的纯日期标题才更新继承日期 |
| 240KB 只活下来 7 行 | 按「(日期, 主题) 聚合后取首条」 | 每个源块产出一行，只把单行压短 |
| 时间线只剩提问、没有动作 | 照搬原文，取到了 `User` 部分 | 取 `Assistant` 部分（`answer_part`），只有存在标记时才切 |
| `v4.8.0`、文件名、域名被截断 | 断句用 `(?<=[.!?])` 无条件切 | 中文句读 + **ASCII 句点必须跟空格**才断 |
| 版本号/数据流被腰斩 | 拿 `→` 当说话人分隔符，而中文技术文本大量用 `→` 表示数据流 | 改用私用区字符 `U+E000`/`U+E001` |
| 同一事实被召回两次 | 同一多行块既进记忆流（首句）又进工作区册（全文） | 按块的自然形态分流：单行短块归时间线，多行结构块归工作区册 |
| 检索结果满屏「条目」 | 时间戳式标题被填成 `'条目'`，标题的关键词贡献归零 | 标题缺失/是元信息时**取正文首句**当标题 |
| 明文密钥/卡号进了每轮注入 | 记忆会被检索并注入，等于把密钥复制到每一次模型请求 | 出库即脱敏；⚠️ 正则**不能用 `\b`**（Python `\w` 含 CJK，中文紧邻数字无单词边界，`卡号4549 2418…` 会漏），一律 `(?<!\d)`/`(?!\d)` |
| 分类总把求职内容判成模型接入 | 正文夹带无关词（「Clash 代理致 502」） | 标题权重 ×3 —— 标题是内容的浓缩 |

### 8.5 Windows 环境与后台进程（「无弹窗铁律」）

| 症状 | 根因 | 修法 |
|---|---|---|
| 后台任务一跑就弹 Windows Terminal 窗口，密集时每秒好几个 | Win11 默认终端是 **Windows 终端**：后台进程一分配控制台就开一个 WT 窗口 | `HKCU\Console\%%Startup` 的 `DelegationConsole` / `DelegationTerminal` 指向 **conhost** |
| 计划任务每次触发闪一下窗 | 动作是控制台程序（`powershell.exe` / `py.exe`），任务计划程序**先建窗口**；`-WindowStyle Hidden` 只是建完再藏，任务属性的「隐藏」勾选同样无效 | 动作改走 `wscript.exe` + `WScript.Shell.Run(cmd, 0, False)`；生成器 `~/.dsh/scripts/hidetasks.py`，回滚清单 `tasks/MANIFEST.json` |
| 按「新进程」判断还在不在弹窗 → 误报 | 隐藏控制台**照样**创建 `conhost.exe` 进程 | 判据用**枚举可见窗口**（`IsWindowVisible` + 新 HWND），不要数进程 |
| 整理完 core 反而变大了 | 模型返回的是旧版本内容（把它自己的新事实丢了） | 确定性校验拦下、拒绝覆盖 —— 见 §2.6 |

> 实测：改造前 90 秒内 **20** 个新可见窗口 → 默认终端改 conhost 后 **1** 个 → 任务全部走 wscript 后 **0** 个。
