# DBA 接入指南

> 给**别的 Agent / 别的项目**接入 DBA 记忆层。
>
> 全文只讲一件事：怎么把 `port/dba.py` 这一个文件接进你自己的流程，
> 并且**不把「记忆层坏了」误读成「记忆里没有这件事」**。
>
> 仓库根默认 `D:\AI\DBA`，可用环境变量 `DBA_HOME` 覆盖。

---

## 一、接入点只有一个文件

| 你该碰的 | 你不该碰的 |
|---|---|
| `port/dba.py` —— 唯一接入门面 | `scripts/nb_*.py` —— 实现，门面内部自己调 |
| `DBA_HOME` 环境变量 —— 唯一路径开关 | `memory/` 下的路径拼接 —— 门面自己定位仓库根 |
| `recall()` / `remember_*()` / `context()` / `status()` | 索引文件名、`.index/`、`.vec/` 的细节 |

门面**只做编排**，不重复实现索引/检索/组装。这样做是为了让「Agent 接口」和
「实现」不会各改一套、慢慢漂移。所以接入方也不需要知道：

- 仓库在哪（`sys.path.insert` 一次即可，门面自己找上一级）
- 索引叫什么（`memory/.index/inverted.json`）
- Ollama 跑没跑（不可用时会在返回值里**说出来**，见第四节）

---

## 二、三步接入（最小示例，照抄可用）

```python
import sys; sys.path.insert(0, r"D:\AI\DBA\port")
import dba

# ① 读：自动选通道
r = dba.recall("查询")                 # → {query,hits,text,channels,degraded,bytes}
print(r["text"])                       # 直接可塞进 prompt

# ② 写：按写入者分工（云端模型 / 本地模型）
dba.remember_core("硬事实", title="标题")          # 核心记忆（云端模型）
dba.remember_stream("干过什么", tag="标签")        # 记忆流（本地模型）
dba.remember_ws("工作区", "细节", title="标题")     # 工作区册（云端模型）
```

三行就通了。下面每一条都是它的展开。

> ✅ **接口诚实性（2026-10-06 已修）**：**五种 mode 现在返回完全相同的键集**
> `query` / `hits` / `text` / `channels` / `degraded` / `bytes` / `note`
> （`narrowed` 出现在 `kw`/`auto`/`ladder`，`model` 出现在 `vec`，
> `relaxed`/`weak`/`weak_reasons`/`time` 出现在 `ladder`），
> 所以 `r["channels"]` 在**任何** mode 下都安全。
>
> 这里曾经是真的坑：单通道走成功路径时直接返回底层实现的原始 dict，
> **没有 `channels` 键**，照文档写 `r["channels"]` 会 `KeyError`。
> 修法是让 `_kw_only` / `_vec_only` 也走统一的返回构造，而不是把内部结构
> 漏给调用方。**门面的职责就是不让底层实现细节漏出去** —— 漏一次，
> 接入方就得为每种 mode 记一套键名。
>
> 若你手上是旧版本代码，请按第 3.3 节核对；现在的版本五模式键集一致。

## 三、`recall()` —— 读

### 3.1 签名

```python
dba.recall(query: str, top_k: int = 5, scope: str | None = None, mode: str = "auto") -> dict
```

`scope` 可取 `"core"` / `"stream"` / `"ws"`。**默认 `None` 时会排除 `core`** ——
核心记忆已经全量注入了，再召回它等于同一份内容占两份注入预算。

### 3.2 五种 mode 的用法与取舍

| mode | 跑什么 | 依赖 | 什么时候用 | 代价 |
|---|---|---|---|---|
| `"auto"`（默认） | 关键词优先；命中**不足**才补向量 | 关键词零依赖；补向量时才要 Ollama | 常规每轮检索 | 快且**省 GPU**（够用就不开向量） |
| `"kw"` | 只走关键词 | 纯 Python 标准库，**零依赖零 GPU** | 离线环境、Ollama 挂了、要精准可解释的命中 | 同义改写查不到 |
| `"vec"` | 只走向量 | **Ollama + GPU**，本机 `bge-m3` 1024 维 | 用户用同义词问同一件事 | 必须起 Ollama；第一次要载模型 |
| `"both"` | 两条都跑并合并 | 同上 | 要查全、要对比两条通道 | 最慢，也最贵 |
| `"ladder"` | **三级检索阶梯**（见 3.2.1） | 同 `kw`（零依赖） | 担心「查不到就没线索」，要它自己放宽条件再查 | 比 `kw` 多跑 1~2 次检索 |

「命中不足」的判据是硬编码的：`len(kw_hits) >= max(3, top_k // 2)` 就直接返回，
**不再碰向量层**。默认 `top_k=5` 时，也就是关键词给到 3 条以上就停。

#### 3.2.1 `ladder` 模式：三级检索阶梯

对应既定的检索规则：**本地模型先检索 → 内容太多则二次详细检索（加时间权重，
越近权重越大）→ 云端模型觉得不清晰可主动再次检索**。三级分别落在：

| 级 | 触发条件 | 做什么 |
|---|---|---|
| ① 一次检索 | 总是 | BM25 top_k，**纯相关度，不掺时间** |
| ② 二次检索 | 命中总量 > `RETRIEVAL_MAX_KB`（6KB） | 收窄到行窗口 **+ 时间权重重排** |
| ③ 主动再检索 | 结果「不清晰」 | 逐级放宽，**最多 2 次** |

**第 ① 级为什么不掺时间**：它决定「谁能进候选集」。掺了时间，同一个查询在不同
日子会给出不同候选集，检索不可复现 —— 排查「上次为什么召回不到」就无从下手。
所以时间权重只在**确实太挤**（②）时才参与，那时它决定的是「谁让位」。

**时间权重算法**（② 内）：

```
权重 = 0.5 ** (距最新日期天数 / 30)      半衰期 30 天，下限 0.5
排序 = 相关度 × 权重                      —— 相乘，不是相加
```

- **参照点是语料内最新日期，不是挂钟**。挂钟意味着系统时间一错、或记忆停更
  一段时间，所有权重一起塌掉，而此时它看起来仍在正常工作（都算得出数）。
- **下限 0.5**：实测语料跨 101 天时最老段落权重 0.0969 → 需 **10.3 倍** BM25
  才能排前面，那等于「新」压过「准」。截到 0.5 后时间最多造成 2 倍倾斜。
- **无日期的段落取中性权重** = 有日期段权重的中位数。该值随记忆增长变化，
  文档不写死具体数值；不是 1.0（那等于宣称它们最新，会挤掉真正的新记忆）。
  `nb_doctor` 会打印当前中性权重。

> ⚠️ `time` 字段存在 ≠ 时间权重生效。语料无日期、或只跨 0 天时全部权重都是 1.0，
> 排序与不加时间完全一致，必须如实报告「未生效」。

**第 ③ 级的「不清晰」是三条可计算信号**（不是模型主观感觉，否则要么永不触发、
要么每次多烧一轮）：

1. **0 命中**；
2. **最高分 < 6.0**（`RETRIEVAL_WEAK_TOP_SCORE`，由 14 个真实查询标定：
   最高分落在 4.25~35.12，6.0 只圈住偏弱的两例，不误伤其余）；
3. **命中段落与查询无共享词** —— 二元分词下「记忆系统」会切成
   记忆/忆系/系统，含「系统」的无关段落也能命中，这条能把这类噪声认出来。

放宽手段逐级为：**放开 `scope` → `top_k` 翻倍**（第 3 级「纳入 core」默认不启用，
因为 core 是全量注入的）。**每次放宽都记进 `relaxed`** —— 放宽本身不是问题，
放宽而不说才是问题。

```python
r = dba.recall("量子纠缠光谱仪", mode="ladder")
r["relaxed"]       # ['top_k 3 → 6']  空列表 = 一次就查到了，没放宽
r["weak"]          # True = 放宽后仍不清晰，云端模型该自己换个说法再查
r["weak_reasons"]  # ['命中段落与查询无共享词（仅二元组擦边命中）']
r.get("time")      # 触发过二次检索才有：权重是否真的生效、跨度几天、提升几条
```

> ⚠️ **`time` 字段存在 ≠ 时间权重起了作用**。若语言料无日期、或只跨 0 天，
> 所有权重都是 1.0，排序与不加时间完全一致。所以 `time` 里带 `span_days` /
> `dated` / `undated`，`note` 也会**如实写「未生效」**。不说明的话，人会以为
> 结果在按新旧排 —— 那是把「没发生」说成「发生了」。

### 3.3 各模式实际返回的键（实测，本机 `D:\AI\DBA`）

| mode | 返回的键 |
|---|---|
| `"auto"` | `query` `hits` `text` `channels` `degraded` `bytes` `narrowed` `note` |
| `"kw"` | `query` `hits` `text` `channels` `degraded` `bytes` `narrowed` `note` |
| `"vec"` | `query` `hits` `text` `channels` `degraded` `bytes` `model` `note` |
| `"both"` | `query` `hits` `text` `channels` `degraded` `bytes` `note` |
| `"ladder"` | 同 `"kw"`，另加 `relaxed` `weak` `weak_reasons`，触发二次检索时另有 `time` |

**核心键集五模式完全一致**（`query` `hits` `text` `channels` `degraded` `bytes` `note`），
模式专属键有四个：`narrowed`（`kw`/`auto`/`ladder` 的二次检索收窄标记）、
`model`（`vec` 的嵌入模型名）、`relaxed`/`weak`/`weak_reasons`（`ladder` 放宽信息）、
`time`（`ladder` 的时间权重是否生效）。标了"专属"的直接用 `.get()` 即可：

```python
r     = dba.recall(q, mode="auto")
text  = r["text"]                  # 成品文本
bad   = r["degraded"]              # 一定存在（可能是空列表）
ch    = r["channels"]              # 一定存在（2026-10-06 起）
extra = r.get("narrowed", False)   # 模式专属，用 .get()
```

`ladder` 的结果还会区分：`relaxed` 是已采纳的放宽，`relax_notes` 是试过但未采纳的放宽（含原因和条数变化）；二者不能混用。
`time` 含 `dated`/`undated`/`neutral_weight`/`min_weight`/`halflife_days`/`span_days`/`promoted`；每条命中的 `dated` 表示确实按日期计算了权重，来自计算处的 `applied`，不是 `date` 字段非空。

`hits` 每项的形状**两条通道不一样**，这是有意的（各自沿用自己实现的既有键名）：

| 字段 | 关键词命中 | 向量命中 |
|---|---|---|
| `file` / `id` / `scope` / `score` / `text` / `source` | ✅ | ✅ |
| `heading` | ✅ | ❌ |
| `head` | ❌ | ✅ |
| `truncated` | ✅（二次检索收窄时为 True） | ❌ |

想同时兼容：`head = h.get("head") or h.get("heading", "")`。
（门面内部渲染 `text` 时就是这么做的，所以**你直接读 `text` 就不用管这些差异**。）

### 3.4 `channels` 怎么读

`channels` 回答的是「**这轮问了谁**」，`degraded` 回答的是「**谁答不上来**」。
两个字段必须分开读，混起来就会把「没问」当成「问了且正常」。

- `["kw"]` —— 只跑了关键词通道。**这不代表向量层是好的**，只代表它这轮没跑
  （`auto` 判据已满足，主动跳过）。
- `["kw", "vec"]` —— 两条都跑了。
- `["vec"]` / `["both"]` 失败时 —— 单通道请求的失败路径也会带 `channels`。

> ⚠️ **`degraded == []` 不能证明向量层健康。**
> `mode="auto"` 在关键词命中充足时**根本不会去问向量层**，此时
> `channels == ["kw"]`、`degraded == []`。这是正常省算力，但不构成体检。
> **要巡检向量层必须显式用 `mode="vec"` 或 `"both"`**（或用 `nb_doctor.py`）。
> 否则「静默降级」会以另一种形式复发：不是少给结果，而是**探针自己不说话**。

### 3.4.1 参数校验：拼错会当场抛 `ValueError`，不会静默兜底

```python
dba.recall("x", mode="vecc")   # ValueError: 未知 mode；只接受 'auto'|'kw'|'vec'|'both'|'ladder'
dba.recall("x", top_k=0)       # ValueError: top_k 必须是 >=1 的整数
dba.recall("x", scope="wss")   # ValueError: 未知 scope；只接受 None|'core'|'stream'|'ws'
```

这三条是**故意抛错**的，都是踩过的坑：

| 拼错 | 旧行为 | 为什么旧行为很坏 |
|---|---|---|
| `mode` | **静默落回 `auto`** | 调用方以为在做语义检索，实际得到关键词结果，且没有任何提示 |
| `top_k=0` / 负数 | 各通道行为不一致 | 关键词返空、向量可能返 1 条 → 调用方拿到自相矛盾的结果 |
| `scope` | **静默返回空命中** | 看起来像「记忆里没这事」，实际是参数错 —— 排查方向完全相反 |

参数写错属于**程序 bug**，必须在第一次运行就炸出来；它不是「记忆里没有」，
两者不可同形。

### 3.5 关于 `"both"` 的合并规则：交错，不是分数相加

```
BM25 分数   →  量纲浮动的「排名分」：换一份语料整体平移，同一分值不具绝对意义
余弦相似度  →  [-1,1] 的「绝对相似度」：有物理意义（同语言相关段落 >0.6，不相关 <0.4）
```

两者**量纲不可比**，所以 `"both"` 的合并是**按各自排名轮流取**（kw 第 1、vec 第 1、
kw 第 2、vec 第 2…），并按内容去重，**不做分数相加**。

理由两条，都是实测踩出来的：

1. **相加会让量纲占优的通道吃掉全部名额。** BM25 的数值区间远大于余弦，
   直接相加排序后向量通道的语义命中基本永远看不到。
2. **拼接（先放完 kw 再放 vec）同样不行。** 关键词通道每次都能返回满 `top_k`，
   拼接等于把名额全占了。

去重也是必须的：同一段落很可能两条通道同时召回，不去重则 `top_k` 会被同一段的
副本占满 —— 看起来命中很多，信息量却没增加。

> 关键词侧的阈值（`RETRIEVAL_MIN_SCORE_RATIO`）是**按本次检索最高分归一**的相对比例，
> 默认 `0.0` = 关闭；向量侧的阈值（`VEC_MIN_SCORE`，默认 `0.45`）是**绝对**余弦值。
> 两边刻意用了不同的尺度，原因和上面一样：BM25 只能相对，余弦可以绝对。

## 四、`degraded` —— 必须检查

### 4.1 为什么必须检查

`degraded` 是**降级报告**，不是调试信息。本项目有一条硬规矩：

> **降级必须是「明确说出来的降级」。绝不允许静默少给结果。**

理由是这个误读链已经造成过实际损失：

```
向量层挂了 → 检索只返回关键词结果 → 命中 0 条
   ↓ 不检查 degraded
「记忆里没有这件事」  ← 错。真相是「语义通道这轮根本没跑」
   ↓
重复问同一件事 / 以为记忆丢了 / 重新记一遍（于是记忆里出现两条重复）
```

静默降级在本项目里出过更狠的一次：日期字段的哨兵值与「无值」共用返回通道，
96 条记录最后只剩 1 条带真日期，**全程没有任何报错**。所以现在：

- 返回值里**永远**有 `degraded`（正常时是空列表 `[]`）；
- 哪条通道没跑，就在里面写一条 `"<通道>:<异常类型>: <原因>"`；
- `"auto"` 模式下**两个通道都没跑成**时，`degraded` 会有两条。

### 4.2 向量层挂了时的真实返回形状

正常态（Ollama 在跑，GPU 可用）：

```python
r = dba.recall("怎么让模型记住我", mode="vec")
# channels : ['vec']
# hits     : 5
# bytes    : 2192
# degraded : []
```

**向量层挂了**（`mode="vec"` 或 `mode="both"`）—— 下面是实测的原样输出：

```python
r = dba.recall("怎么让模型记住我", mode="vec")
r["channels"]   # ['vec']
r["degraded"]   # ['vec:VecUnavailable: 连不上 Ollama（http://127.0.0.1:11434）：<urlopen error
                #  [WinError 10061] 由于目标计算机积极拒绝，无法连接。>
                #   起服务: ollama serve
                #   拉模型: ollama pull bge-m3']
r["hits"]       # []
r["bytes"]      # 0
r["note"]       # '向量通道不可用'
r["text"]       # ''
```

**读法**：`degraded[0]` 的格式是 `通道:异常类型: 原因`。上例拆开就是
通道 `vec`、异常 `VecUnavailable`、原因「连不上 Ollama」，
并且原因里**自带修复命令**（`ollama serve` / `ollama pull bge-m3`）。

`auto` 模式下如果关键词够用，向量层压根不会被调用，`degraded` 是空列表：

```python
r = dba.recall("怎么让模型记住我", mode="auto")
r["channels"]   # ['kw']        ← 关键词给够了 5 条，向量这轮没跑
r["degraded"]   # []           ← 空列表 ≠ 向量层健康
```

⚠️ **这条最容易被误读**：`auto` 的 `degraded == []` 只说明「这轮没有任何通道失败」，
不说明「向量层可用」。要**主动体检**向量层，就得显式跑 `mode="vec"` 或 `"both"`。

### 4.3 接入方该写的最小代码

```python
import sys; sys.path.insert(0, r"D:\AI\DBA\port")
import dba

r = dba.recall(user_input, mode="auto")
if r["degraded"]:
    for d in r["degraded"]:
        log.warning("DBA 记忆检索降级: %s", d)      # 必须留痕，不要吞掉
if r["hits"]:
    prompt_tail = r["text"]
elif r["degraded"]:
    # 关键区分：命中为空 且 有降级 → 「没查成」，不是「没记过」
    log.warning("检索为空但存在降级，不能断言「记忆里没有这件事」")
else:
    log.info("两条通道都正常，确实没有相关记忆")
```

**最后那个 `elif` 是整个第四节的重点**：只有「`hits` 为空」**且**「`degraded` 为空」
才允许下「记忆里没有」的结论。

## 五、写入：分工与闸门

### 5.1 谁能写哪一层（这是本架构的核心约束）

| 层 | 文件 | 写入者 | 函数 | 容量 | 消费方式 |
|---|---|---|---|---|---|
| 核心记忆 | `memory/core.md` | **云端模型** | `remember_core(text, title="追加")` | **≤15KB 硬上限** | **每轮全量注入**，不检索 |
| 记忆流 | `memory/stream.md` | **本地模型** | `remember_stream(text, tag="")` | 不限 | 仅检索，**一行一条** |
| 工作区册 | `memory/ws/<区>.md` | **云端模型** | `remember_ws(area, text, title=None)` | 不限 | 仅检索，存细节 |

**为什么这样分（不是笔误，也不是分工洁癖，是信息可得性决定的）：**

- `core` / `ws` 要的是**提炼** —— 把一轮对话压成一条硬事实、或写成一份细节纪要。
  这需要看得见**完整上下文**，只有云端模型做得到。
- `stream` 要的是**不间断的流水**，而且**每轮都要写**，所以必须极便宜、必须常驻。
  这件事归本地模型。

容量的分法同理：`core` 是**全量注入**，所以必须硬限 15KB；另两层**只被检索**，
所以不限长度 —— 它们的增长不推高每轮 token 成本。这是本架构与旧「五级记忆」
（层层压缩、层层有配额）最根本的区别：**注入量随话题浮动，不随记忆总量增长。**

写法上，**三个函数名故意不一样**，就是为了让这个约束**写进代码而不是文档**。

### 5.2 反例：把细节写进 `stream` 会怎样

**错误写法**（把一整段工作纪要塞进记忆流）：

```python
dba.remember_stream(
    "复查 nb_vec.py 的 load()：发现 npy 行数与 meta.count 不一致时会返回错位的段落，"
    "危险在于它不报错，只是内容对不上。改成行数不等即整份判损坏，抛 VecCorrupt。"
    "顺带发现 np.save() 见到 .tmp 结尾会自动补 .npy，于是文件落在 vectors.npy.tmp.npy，"
    "而 replace 找的是 vectors.npy.tmp → FileNotFoundError……"
)
```

逐条说清它坏在哪：

| 后果 | 具体表现 |
|---|---|
| **淹掉记忆流** | `stream.md` 的价值在「**一行一条、可被检索定位**」。细节一进来，它就从「索引」变成「又一本流水账」，条目长度参差，定位性消失。 |
| **占掉检索名额** | 检索是 `top_k` 截断的。一条巨长条目进榜，等于挤掉若干个本来能被定位到的真事件。 |
| **写作成本倒挂** | `stream` 归本地模型写、要求**每轮都写**。让它产出长纪要，等于让最便宜的那条路径干最贵的活。 |
| **走错闸门** | 细节内容往往撞上写入闸门（见下），要么被拒、要么被削成没头没尾的半句。 |

**正确写法**（流水进 `stream`，细节进 `ws`）：

```python
dba.remember_stream("修完 nb_vec.load 的行数校验", tag="记忆系统")
dba.remember_ws("记忆系统", "load() 原来在 npy 行数与 meta.count 不一致时……", title="向量索引损坏判定")
```

### 5.3 记忆流的写入闸门会拒收什么

`remember_stream` 前有内容闸门，命中即**拒绝写入并抛出 `WriteError`**，一个字节都不落盘。
被拒的类别（全部实测）：

| 类别 | 例子 | 判定 |
|---|---|---|
| **对话残片** | `5.5呢？   测完了，结论很干脆 —— 5.5 进不了 DSH` | 没头没尾的问答残片，不是「干过什么」 |
| **系统报错** | `Hermes hit repeated errors and stopped this turn so it wouldn't...` | 运行时报错文本 |
| **空话** | `ok` / `好的` / `收到` / `继续` / `done` / `yes`（整条就是这类词） | 无信息量 |
| **裸链接 / 裸密钥** | 整条只有一个 `https://...` 或 `sk-...` / `ghp_...` | 不是工作记录，且不该留进记忆 |
| **过短碎片** | 长度 < 8 字符 | 信息量不足以定位「干过什么」 |

拒收时抛出的文案会**带着原因和去处**，例如：

```
stream 拒收：过短（5 字符），信息量不足以定位「干过什么」
  内容: 测完了
  细则请写 ws 册：py nb_write.py ws <区> "..."
```

其余会被拒的**空值/非法参数**（这一类是「调用方少传了参数」，门面一律报错、**不做兜底**）：

| 传了什么 | 结果 |
|---|---|
| `remember_stream("")` | 拒收：正文为空（空行会在记忆流里留下无信息条目） |
| `remember_ws("", "...")` | 拒收：`area` 为空，**不会兜底到 `misc`** |
| `remember_ws("a/b", "...")` | 拒收：`area` 含非法字符，**不做静默删除** |
| `remember_ws("CON", "...")` | 拒收：Windows 保留设备名（裸设备名会让 `open()` 报成功但盘上没有文件 = 静默丢数据） |
| `remember_stream("...", at="")` | 拒收：`--at` 给了空值。**想用当前时间就不传 `at`，不传 ≠ 传空串** |
| `remember_core("")` | 拒收：正文为空（会在 `core.md` 里留下空段污染文件） |

> 为什么空值一律报错：兜底会把不同来源的数据糊进同一个文件，事后**再也分不开**。
> 实测 `misc.md` 已经因此变成一本 16.4KB 的真实工作区册，两条来源在里面无从分辨。

### 5.4 写入后的索引

- `remember_stream` / `remember_ws` 之后**自动重建关键词索引**（索引小，毫秒级），
  所以下一次 `recall` 立刻能查到。
- 若重建失败，内容**已经落盘**，只是检索暂时看不到它 —— 此时会明确区分
  「写成功 / 索引没更新」，并提示跑一次 `reindex`。**不要重写内容**（会在记忆流里留下重复条目）。
- **向量索引不会自动重建**。写完新内容后，向量通道仍是旧的，需要显式重建
  （见第七节「关键词索引陈旧」与 `dba.reindex()`）。

## 六、接进 prompt 的正确姿势

### 6.1 必须分两段，且顺序固定

```python
c = dba.context(query)      # 一次调用同时给你两段
# c["core_text"]  → 稳定段：核心记忆（≤15KB，全量），注入在 prompt【前部】
# c["hits_text"]  → 变化段：本轮检索命中，注入在 prompt【最末尾】
```

**绝不能自己拼成一段。** 两段的变化频率完全不同：

| 段 | 变化频率 | 该排在哪 |
|---|---|---|
| `core_text`（核心记忆） | **几天**才变一次 | prompt **前部**，做稳定前缀 |
| `hits_text`（检索命中） | **每轮**随用户输入变 | prompt **最末尾** |

### 6.2 为什么：前缀缓存

云端模型的前缀缓存是**按前缀逐字节比对**的。一旦某处发生变化，
从该处起**其后所有内容**的缓存全部失效。

```
✅ 正确：稳定在前、变化在后
   [系统指令] [core_text 稳定] [工具定义] [人格段] [hits_text 本轮]
                                                       ↑ 只有这一段每轮重算
   → 实测缓存命中率 92.7%

❌ 错误：两段拼成一段（或把变化内容放前面）
   [系统指令] [core_text + hits_text 合成段] [工具定义] [人格段]
                    ↑ 检索一命中，从这一处起全变
   → 其后所有段落的缓存全废 → 实测命中率 0%
```

同样的原因，**时间戳之类的每轮变量绝不能进前缀**。组装产物的第一行
（`<!-- Notebook core | built: ... -->`）之所以要能被下游精确剥掉，就是为了
不让每轮变化的构建时间留在注入正文里。**自己接入时也别把时间戳写进稳定段。**

### 6.3 伪代码

```python
import sys; sys.path.insert(0, r"D:\AI\DBA\port")
import dba

def build_prompt(user_input, tools_def, persona):
    # ① 一次调用拿到两段
    c = dba.context(user_input, top_k=5)

    parts = []
    parts.append(SYSTEM_INSTRUCTIONS)          # 固定
    parts.append(c["core_text"])               # 稳定段（几天一变）
    parts.append(tools_def)                    # 固定
    parts.append(persona)                      # 固定

    if c["core_missing"]:                      # 🚨 core.md 不存在 → 全量注入失效
        log.error("DBA 核心记忆缺失，本轮「核心记忆」是空的")

    # ② 变化段一律排最末，单独一段，绝不与上面任何一段合并
    if c["hits_text"]:
        parts.append(c["hits_text"])           # 每轮都变 → 放最末

    return "\n\n".join(parts), c
```

要点复述：

1. **`hits_text` 单独成段、排最末**，不要插进 `core_text` 或工具定义之间。
2. `core_text` 要能**按会话缓存** —— 同会话中途不必重新拼它。
3. `dba.context()` 已经做了 `{{` 逃逸（打断成 `{{\u200b`），因为 DSH 那类
   system-prompt 插值器遇到未注册变量会**整轮抛错**。别的框架如果也做 `{{var}}`
   插值，别把这一步去掉。
4. **注入总量有硬上限**，别把两段无脑全塞进去：

| 预算项 | 值 | 行为 |
|---|---|---|
| 核心记忆上限 | **15KB** | 超出时 `core_text` 里会带告警段，但**不会静默丢弃** |
| 注入硬上限 | **64KB** | 超限下游会**整段丢弃**（记忆静默消失且不报错） |
| 告警起点 | **48KB**（64KB × 0.75） | 到此处 `budget_warning` 开始非空 |

```python
if c["budget_warning"]:
    log.error("DBA 注入预算告警: %s", c["budget_warning"])
if c["core_over"]:
    log.warning("核心记忆 %sKB 已超 15KB 上限，需压缩（细则移入工作区册）", c["core_kb"])
```

**别忽略 `core_over`**：`core.md` 是每轮全量注入项，它超限是**每轮**都在花的钱。

### 6.4 云端模型主动二次检索（已实现，两种用法）

一轮注入不等于查得够。检索不清晰时，云端模型**应当**发起第二次检索 ——
这是设计内的行为，不是绕过。

**用法 A：交给 `ladder` 自动放宽**（推荐，见 3.2.1）。它在结果「不清晰」时
自己逐级放宽并查清楚，你只需检查 `weak`：

```python
r = dba.recall(user_input, mode="ladder")
if r["weak"]:
    # 自动放宽后仍不清晰 → 才需要你换个说法/换通道再查
    log.warning("检索仍不清晰: %s", r["weak_reasons"])
```

**用法 B：自己换角度再查。** 自动放宽只动「范围/条数」这类**机械条件**，
不动**语义**；换同义词、换通道这类需要理解的事仍归你：

```python
dba.recall("代理地址", scope="ws", mode="kw")     # 只查工作区册
dba.recall("待办",     scope="core", mode="kw")   # 显式查核心记忆（默认是排除的）
dba.recall("怎么让模型记住我", mode="vec")         # 关键词没命中 → 试语义
```

> ⚠️ **放宽过就必须知道放宽过**。`ladder` 会把每次放宽写进 `relaxed`；
> 若你手动换说法重查，也请把「这是第二次查、和第一次不是同一批结果」记下来。
> 把「放宽后才找到的」与「一次就精确命中的」混作一谈，等于是给了一个
> 比实际更确定的答案。

## 八、常见故障表

`degraded` 里的每一条都形如 `"<通道>:<异常类型>: <原因>"`。
先按**异常类型**定位，再照命令修。

| 症状（`degraded` 里的内容） | 原因 | 命令 |
|---|---|---|
| `vec:VecUnavailable: 连不上 Ollama（http://127.0.0.1:11434）：<urlopen error [WinError 10061] ...>` | Ollama 没起 / 端口不对 | `ollama serve`；确认 `VEC_OLLAMA_URL` 指向 `http://127.0.0.1:11434` |
| `vec:VecUnavailable: Ollama 返回里没有 embeddings` | 模型没拉下来 | `ollama pull bge-m3` |
| `vec:VecUnavailable: Ollama 嵌入超时（bge-m3），可能在跑 CPU 或模型过大` | 嵌入任务落到 CPU | 查 GPU 占用；本项目**不做 CPU 兜底**，拿不到 GPU 就直接报错 |
| `vec:VecUnavailable: 向量索引不存在，先建：py nb_vec.py build` | `.vec/` 下缺 `vectors.npy` 或 `meta.json`（新建仓库 / 被清过） | `py -3.14 D:\AI\DBA\scripts\nb_vec.py build` |
| `vec:VecCorrupt: 行数不一致：npy 508 行 vs meta 400 条 → 行与元数据已错位，必须重建` | 向量索引**损坏**：上次写入被打断，只换了其中一个文件 | 必须重建：`py -3.14 D:\AI\DBA\scripts\nb_vec.py build` |
| `vec:VecCorrupt: meta.json 读不出 / 缺字段 'count'（半写文件？）/ vectors.npy 维度不对` | 同上，损坏形态之一 | 同上，重建 |
| `vec:VecCorrupt: query 维度 1024 与索引维度 768 不符 → 嵌入模型换了？重建` | 换了嵌入模型（维度变了），旧索引不再可比 | 重建向量索引：`py -3.14 D:\AI\DBA\scripts\nb_vec.py build` |
| 刚写的内容检索不到（`degraded` 为空、`hits` 里没有它） | 关键词索引陈旧 / 上次重建失败 | `py -3.14 D:\AI\DBA\scripts\nb_write.py reindex` |
| 新写的内容只在 `mode="kw"` 查得到、`mode="vec"` 查不到 | 向量索引比数据旧（**写完不会自动重建向量索引**） | `py -3.14 D:\AI\DBA\scripts\nb_vec.py build` |
| `status` 里显示 `core 🚨 缺失! core.md 不存在 → 全量注入失效` | `core.md` 被删 / 路径不可达 | 确认 `D:\AI\DBA\memory\core.md` 存在；从 `backups/` 或 `ws/` 册恢复；确认 `DBA_HOME` 没指错 |
| `kw:...` 开头的降级 | 关键词层坏了（纯标准库零依赖，坏了就是代码/索引真坏了） | `py -3.14 D:\AI\DBA\scripts\nb_write.py reindex`；仍失败则查 `nb_search.py` / `nb_index.py` |
| `hits` 为空且 `degraded` 为空 | **这才是真的「没记过」** | 不必修 —— 但先确认第七节 ④ 的向量体检也过了 |

命令速查（全部真实存在）：

```powershell
py -3.14 D:\AI\DBA\port\dba.py status                        # 三层 + 两条通道 + GPU
py -3.14 D:\AI\DBA\scripts\nb_write.py list                  # 三层文件现状
py -3.14 D:\AI\DBA\scripts\nb_write.py reindex               # 重建关键词索引
py -3.14 D:\AI\DBA\scripts\nb_vec.py build                   # 重建向量索引（需 Ollama+GPU）
py -3.14 D:\AI\DBA\scripts\nb_vec.py stats                   # 向量层：段数/维度/是否陈旧/GPU
py -3.14 D:\AI\DBA\scripts\nb_search.py "查询词" --top-k 5 --json
```

`dba.reindex()` 是把两条索引一起重建的便捷入口：

```python
dba.reindex()                  # {"kw": "...", "vec": {...}}   两条都重建
dba.reindex(vectors=False)     # 只重建关键词（毫秒级，不需要 GPU）
```

> ⚠️ 别把「查不到」当「不存在」。本项目有三次静默降级事故，都是同一个病：
> **失败与真实取值共用了一个返回通道**。`degraded` 字段存在的唯一目的，
> 就是让这个区分在**每一次**调用里都成立。
