# 迁移记录

这份文档记的是**为什么**会变成现在这样，以及过程中踩了什么坑。
将来读到某段代码觉得「这写得也太小心了」时，答案多半在这里。

## 三代架构

| 代 | 时间 | 结构 | 容量策略 |
|---|---|---|---|
| 一 | 2026-08 | **五级记忆** F0/L1/L2/L3/L4 | 层层有配额，容量驱动降级 |
| 二 | 2026-10-05 | **记事本三层** core/stream/ws | 只有 core 设限（15KB），另两层不限长 |
| 三 | 2026-10-06 | **DBA 双脑架构** = 记事本三层 + 向量层 + 可移植仓库 | 同二代，另加语义检索通道 |

### 为什么废弃五级记忆

五级的设计是「容量满了就把最老的压到下一层」：L1 满 → 压缩进 L2 → L2 满 → 压进 L3。
问题不在实现，在**前提**：

1. **它假设记忆总量必须受限**，因为每轮都要把全部记忆塞进 prompt。所以每层都要
   设配额、都要写压缩逻辑，维护成本随层数平方增长。
2. **压缩即丢弃**。为了腾地方而按「整段丢弃最旧的块」删内容，那是**丢记忆**，
   不是压缩。用户明确反对过：「压缩必须是 LLM 摘要/提炼，不是原始内容搬家到下一级」。
3. **注入量随记忆总量增长**。记忆越多，每轮 prompt 越大，成本线性上升。

记事本三层把第 3 点整个换掉了：**只有 core 全量注入（硬限 15KB），
stream/ws 只被检索**。于是注入量**随当前话题浮动，不随记忆总量增长** ——
磁盘上 249KB 的记忆，每轮实际只注入约 21KB。这个比例只会继续拉大。

这就是为什么 stream/ws **不限长度**：它们的增长不再推高每轮 token 成本，
所以没有任何理由限制它们，也就没有压缩这一步。**没有压缩，就没有压缩的 bug。**

### 三代为什么还要加向量层

关键词索引是精确 token 匹配。实测它查不到同义改写：

```
查「怎么让模型记住我」 → 关键词 0 命中（记忆里没这几个字）
                        → 向量 0.594（命中的是「记忆连续性」相关段落）
```

另测：「代码是谁写的」「投简历给机器人公司」「上网要翻墙吗」——关键词全 0 命中，
向量分别给出 0.520 / 0.675 / 0.524 的合理结果。

### 搬了什么

| | 从 | 到 |
|---|---|---|
| 记忆数据 | `%LOCALAPPDATA%\hermes\memories\notebook\`（junction → `D:\AI\snowfox-memory\memories`） | `D:\AI\DBA\memory\` |
| 工具链 | `~/.dsh/scripts/nb_*.py` | `D:\AI\DBA\scripts\` |
| 定时任务入口 | 同上 | `memory-daily.ps1` 改为转发到 DBA |
| 客户端适配器 | `~/.dsh/profiles/web/`、`hermes/plugins/` | 生效位置不变，仓库内留副本 `integrations/` |

### 为什么要搬

记忆是**可移植资产**，而 `hermes` 只是某一台机器上某一款客户端程序的安装目录。
把记忆埋在别人家目录里等于要求：所有接入的 Agent 都装同一款客户端、
并且遵守它的目录习惯。换客户端就得搬一次家，而搬家正是最容易丢数据的时候。

现在的约束是 **数据跟着代码走**：默认就在仓库内，`DBA_HOME` 可覆盖。
整个目录拷走 / `git clone` 即用。

### 迁移中真实踩到的坑

**1. 守卫因路径搬走而失效（最危险）**

`mem_compress.py` 有个迁移守卫：检测到新架构就拒绝运行。判据是
`os.path.exists(HH + "/memories/notebook/core.md")` —— 写死了旧路径。
搬到 DBA 后这个判断**永远返回 False**，守卫失效，脚本会认为「还在旧架构下」，
然后去改写 `recent.md`/`summary.md` 这些已废弃的文件。

它**看起来一切正常**（exit 0、有输出），只是偷偷动了旧数据。
修法：先问 `nb_config`（唯一真源），问不到再退回路径探测；且宁可误跳过
（最坏是不干活）也不可漏判（那是写坏记忆）。

**教训**：迁移时，**所有「检测 XX 是否存在」的判据都是定时炸弹**。
路径一改，它们不会报错，只会静默变成相反的答案。

**2. 运行中的进程还持有旧代码**

插件文件改完了，但 DSH / Hermes 是**启动时**把插件读进内存的。
实测：Hermes 网关（旧进程）还在往已废弃的 `recent.md` 写东西，日志显示
`[snowfox] wrote to recent.md`，而代码已经改成写 DBA 了。
必须**重启客户端**，改文件不够。

发现方式：看 `recent.md` 的 mtime 比最后一次代码修改还新。

**3. 两份数据并存**

搬完 data 后旧目录还在，于是同时存在两份「记忆」。这是最坏的状态：
两边都能被读到，谁也不知道哪份是真的。处理方式是**改名而不是删除** ——
`notebook` → `notebook.superseded-20261006`。留作备份，但任何按名字读
`notebook/` 的代码都会失败（显式），而不是读到过期数据（静默）。

## 迁移后的架构决策

### 为什么两个索引零耦合

向量层依赖 Ollama 进程 + GPU；关键词层是纯 Python 零依赖。如果串在一个入口里，
**Ollama 一挂就整个检索全哑** —— 连本来能用的精确检索也没了。

所以：各自独立建索引、独立检索、各自可单独工作。任一方挂了，另一方照常返回，
且结果里**明确标出哪条通道降级了**。

### 为什么降级必须说出来

这是本项目反复踩的同一类坑：**失败与真实取值共用返回通道**。

| 事故 | 静默失败的表现 |
|---|---|
| `date_of()` 用 `'未标日期'` 当哨兵 | 96 条记录只剩 1 条带真日期 |
| `load()` 用 `None` 同时表示「不存在」和「损坏」 | 损坏的索引被判「新鲜」，永久返回 0 命中 |
| `kb()` 用 `0.0` 同时表示「不存在」和「0 字节」 | `core.md` 被删时超限告警失效 |
| `reindex()` 用 stdout-or-stderr 作通道 | 子进程崩溃被当成正常输出 |

现在各自独立异常类型：`MissingSize` / `IndexCorrupt` / `VecCorrupt` / `VecUnavailable`。
**新代码照此办理。**

### 为什么 `degraded` 空不等于健康

`recall(mode="auto")` 在关键词命中充足时**根本不会去问向量层**。
此时 `channels == ["kw"]`、`degraded == []` —— 这是正常的省算力行为，
**但不构成向量层的健康检查**。

要巡检向量层必须显式用 `mode="vec"` 或 `"both"`。否则「静默降级」会以另一种
形式复发：不是少给结果，而是**健康探针自己不说话**。

为此 `channels` 与 `degraded` 是两个独立字段：
- `channels` 回答「这轮问了谁」
- `degraded` 回答「谁答不上来」
